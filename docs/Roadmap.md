**Версия документа:** 1.7
**Дата обновления:** 16 мая 2025 г.
**Статус документа:** Обновлен в соответствии с ТЗ v1.7

## 1. Общие сведения о проекте

### Миссия проекта
- **Долгосрочная миссия**: Сделать 1 миллион человек счастливее к 2030 году
- **Долгосрочная цель платформы**: Предоставить предпринимателям комплексный инструмент ("единое окно") для эффективного управления бизнесом, снижения стресса, экономии времени и ресурсов, а также создания условий для личного благополучия и благополучия команды
- **Бизнес-цель (долгосрочная)**: Выйти на чистый доход 10 млн рублей в месяц

### Цели проекта
- **Отказ от MVP**: Запустить функционально насыщенную полноценную версию платформы в течение 40 недель (10 месяцев)
- Предоставить предпринимателям возможность решать широкий спектр операционных задач через консьерж-сервис
- Обеспечить доступ к проверенным подрядчикам и шаблонам документов
- Реализовать продвинутые функции управления бизнесом и инструменты аналитики
- Внедрить детальную аналитику пользовательского поведения
- Обеспечить надежную и безопасную работу платформы с учетом всех требований
- Экономить время предпринимателей и снижать их стресс

### Целевая аудитория
- Предприниматели (владельцы малого и среднего бизнеса) в РФ
- Их команды (с полноценным функционалом для сотрудников)

### Модель управления техническим долгом
- Выделение 20% времени в каждом спринте на управление техническим долгом
- Категоризация технического долга по приоритетам:
  - **Критический**: Непосредственно влияет на безопасность, стабильность или производительность (решать немедленно)
  - **Высокий**: Негативно влияет на качество кода или усложняет дальнейшую разработку (планировать в ближайших спринтах)
  - **Средний**: Ухудшает поддерживаемость кода (планировать на основе соотношения ценность/усилия)
  - **Низкий**: Несоответствие лучшим практикам, но без значительного влияния (решать при возможности)
- Ведение реестра технического долга с отслеживанием:
  - Описание проблемы и причины ее возникновения
  - Оценка рисков и потенциального влияния
  - Предполагаемое решение и трудозатраты
  - Приоритет и планируемый спринт для исправления
- Регулярные ревью технического долга (каждые 4 недели)
- Обязательное исправление технического долга перед добавлением новых функций в затронутые компоненты

## 4. Стандартизация формата ошибок API

### Общий подход к стандартизации API-ошибок
- Использование единого формата JSON для всех ошибок API
- Семантическое использование HTTP-статусов
- Контекстная информация для отладки
- Локализуемые сообщения для пользователей
- Уникальные коды ошибок для идентификации

### Структура ошибки API
```json
{
  "statusCode": 400,                         // HTTP-статус
  "error": "VALIDATION_ERROR",               // Тип ошибки
  "message": "Ошибка валидации входных данных.", // Сообщение для пользователя (локализованное)
  "details": [                               // Детализированная информация (опционально)
    { 
      "field": "email", 
      "message": "Поле Email должно быть действительным адресом электронной почты.", 
      "code": "INVALID_EMAIL_FORMAT" 
    },
    { 
      "field": "password", 
      "message": "Пароль должен содержать не менее 8 символов.", 
      "code": "PASSWORD_TOO_SHORT" 
    }
  ],
  "timestamp": "2025-05-15T10:30:00.123Z",   // Временная метка
  "path": "/auth/register",                  // Путь запроса
  "correlationId": "abc123xyz789-correlation-id" // ID для трассировки в логах
}
```

### Категории HTTP-статусов
- **4xx** - Ошибки клиента (неправильный запрос)
  - **400** - Bad Request (невалидные данные)
  - **401** - Unauthorized (требуется аутентификация)
  - **403** - Forbidden (недостаточно прав)
  - **404** - Not Found (ресурс не найден)
  - **409** - Conflict (конфликт с текущим состоянием ресурса)
  - **422** - Unprocessable Entity (семантически некорректный запрос)
  - **429** - Too Many Requests (превышение лимита запросов)

- **5xx** - Ошибки сервера (проблемы на стороне API)
  - **500** - Internal Server Error (общая ошибка сервера)
  - **502** - Bad Gateway (ошибка в интеграциях)
  - **503** - Service Unavailable (сервис временно недоступен)
  - **504** - Gateway Timeout (таймаут в интеграции)

### Обработка ошибок
- Централизованная обработка на уровне API-приложения через глобальные фильтры (NestJS)
- Логирование всех ошибок с полным контекстом
- Трассировка ошибок через сервисы с использованием correlationId
- Структурированные и человекочитаемые сообщения для конечных пользователей
- Скрытие технических деталей от пользовательских сообщений об ошибках

## 5. Детализация стратегии тестирования

### Общие принципы тестирования
- **Тестирование как неотъемлемая часть процесса разработки**
  - Приоритет автоматизации для обеспечения надежных регрессионных проверок
  - Сопровождение всех новых функций и исправлений соответствующими тестами
  - Минимум 80-85% покрытия для критически важной бизнес-логики

### Виды тестирования и их применение
- **Unit-тесты (Модульные тесты):**
  - **Ответственность:** Разработчики
  - **Инструменты:** Jest, Vitest
  - **Цель:** Проверка корректности отдельных модулей, функций, компонентов в изоляции

- **Интеграционные тесты:**
  - **Ответственность:** Разработчики, QA-инженеры
  - **Инструменты:** Supertest, Testing Library
  - **Цель:** Проверка взаимодействия между несколькими модулями или компонентами

- **Компонентные тесты (Frontend):**
  - **Ответственность:** Frontend-разработчики
  - **Инструменты:** React Testing Library, Jest/Vitest
  - **Цель:** Тестирование отдельных UI-компонентов React

- **API-тесты:**
  - **Ответственность:** QA-инженеры, разработчики
  - **Инструменты:** Postman, Supertest
  - **Цель:** Проверка полноты и корректности работы API эндпоинтов

- **End-to-End тесты:**
  - **Ответственность:** QA-инженеры
  - **Инструменты:** Cypress, Playwright
  - **Цель:** Тестирование полных пользовательских сценариев 

- **Тестирование производительности:**
  - **Ответственность:** QA-инженеры, DevOps-инженеры
  - **Инструменты:** k6, JMeter
  - **Цель:** Оценка скорости отклика и стабильности под нагрузкой

## 6. Стратегия для мобильных устройств

### Подход к мобильной разработке
- **Progressive Web App (PWA)** вместо нативных мобильных приложений:
  - Единая кодовая база для всех платформ
  - Меньшие затраты на разработку и поддержку
  - Возможность использования без установки
  - Поддержка оффлайн-режима для критических функций

### Ключевые компоненты мобильной стратегии
- **Адаптивный дизайн**:
  - Mobile-first подход к проектированию интерфейсов
  - Автоматическое масштабирование и перестроение интерфейса
  - Оптимизированные компоненты для тачскрин-ввода
  - Учет особенностей мобильного отображения контента

- **Оптимизация производительности**:
  - Минимизация размера бандлов JavaScript
  - Ленивая загрузка компонентов и роутов
  - Оптимизация изображений и медиа-контента
  - Использование Service Worker для кеширования ресурсов

- **Оффлайн-функциональность**:
  - Доступ к ключевым функциям без подключения к интернету
  - Локальное кеширование критически важных данных
  - Синхронизация изменений при восстановлении соединения
  - Визуальная индикация режима работы (онлайн/оффлайн)

- **Нативный опыт**:
  - Поддержка Push-уведомлений
  - Доступ к API устройства (камера, геолокация)
  - Быстрый доступ через иконку на домашнем экране
  - Плавные анимации и переходы

### Этапы реализации мобильной стратегии
1. **Базовый адаптивный дизайн** (Этап 1-2)
   - Разработка адаптивных компонентов UI
   - Тестирование на различных размерах экрана

2. **Расширенная адаптация** (Этап 3)
   - Оптимизация пользовательских сценариев для мобильных устройств
   - Адаптация форм и интерактивных элементов

3. **Полноценный PWA** (Этап 4)
   - Внедрение Service Worker
   - Настройка манифеста и оптимизация для установки
   - Реализация оффлайн-функциональности

4. **Финальная оптимизация** (Этап 5)
   - Оптимизация производительности
   - Расширение оффлайн-возможностей
   - Интеграция с нативными API устройств
