# Git Flow: Модель ветвления для проекта Happyness

В проекте Happyness мы используем модель ветвления Git Flow для организации системы контроля версий. Данный документ описывает основные принципы и рабочий процесс для всех участников проекта.

## Основные ветки

- **master** - основная ветка, содержащая стабильный релизный код. Коммиты напрямую в эту ветку запрещены.
- **develop** - ветка разработки, содержащая последние изменения для следующего релиза. Все фичи и исправления интегрируются в эту ветку.

## Вспомогательные ветки

### Ветки функций (feature branches)

- **Именование**: `feature/имя-функции`
- **Ответвляются от**: `develop`
- **Вливаются в**: `develop`
- **Назначение**: разработка новых функций и возможностей
- **Правила**:
  - Ветка создаётся для каждой новой функции
  - После завершения вливается обратно в `develop`
  - Настройте проверки перед слиянием (линтинг, тесты)

```bash
# Создание ветки фичи
git checkout develop
git checkout -b feature/auth-system

# После завершения работы
git checkout develop
git merge --no-ff feature/auth-system
```

### Ветки релизов (release branches)

- **Именование**: `release/x.y.z`
- **Ответвляются от**: `develop`
- **Вливаются в**: `master` и `develop`
- **Назначение**: подготовка к выпуску новой версии
- **Правила**:
  - В этой ветке можно исправлять только баги
  - Нельзя добавлять новые функции
  - После финализации релиза, ветка сливается в `master` и `develop`

```bash
# Создание релизной ветки
git checkout develop
git checkout -b release/1.0.0

# После завершения работы
git checkout master
git merge --no-ff release/1.0.0
git tag -a 1.0.0 -m "Version 1.0.0"
git checkout develop
git merge --no-ff release/1.0.0
```

### Ветки исправлений (hotfix branches)

- **Именование**: `hotfix/x.y.z` или `hotfix/bug-description`
- **Ответвляются от**: `master`
- **Вливаются в**: `master` и `develop`
- **Назначение**: срочное исправление критических ошибок в продакшене
- **Правила**:
  - Создаются для быстрого исправления ошибок в производственной версии
  - После исправления сливаются и в `master`, и в `develop`

```bash
# Создание ветки хотфикса
git checkout master
git checkout -b hotfix/1.0.1

# После завершения работы
git checkout master
git merge --no-ff hotfix/1.0.1
git tag -a 1.0.1 -m "Version 1.0.1"
git checkout develop
git merge --no-ff hotfix/1.0.1
```

## Правила для коммитов

Мы используем стандарт [Conventional Commits](https://www.conventionalcommits.org/) для создания понятной истории коммитов:

```
<тип>[опционально область]: <описание>

[опционально тело]

[опционально подвал]
```

Типы коммитов:
- **feat**: новая функциональность
- **fix**: исправление бага
- **docs**: изменения в документации
- **style**: форматирование, отсутствующие точки с запятой и т.д.
- **refactor**: рефакторинг кода
- **test**: добавление тестов
- **chore**: обновление задач сборки, настройка менеджера пакетов и т.д.

Примеры:
```
feat(auth): добавлена система аутентификации

fix(api): исправлено некорректное форматирование даты в ответах API

docs: обновление README.md с инструкциями по установке
```

## Защита основных веток

Для `master` и `develop` веток настроены правила защиты:
- Прямые коммиты запрещены
- Изменения вносятся только через Pull Request
- Pull Request должен иметь как минимум одно подтверждение (approve)
- CI проверки (линтинг, тесты) должны успешно проходить

## Рабочий процесс разработчика

1. Создаете новую ветку функции из `develop`
2. Работаете в этой ветке, делаете коммиты
3. Регулярно обновляете свою ветку из `develop` (rebase или merge)
4. По завершении, создаёте Pull Request в `develop`
5. После проверки код сливается в `develop`
6. Ветка функции удаляется после слияния

## Выпуск новой версии

1. Создаётся ветка релиза из `develop`
2. Исправляются баги, обновляется версия и документация
3. После завершения подготовки, релизная ветка сливается в `master` и `develop`
4. Версия в `master` тегируется
5. Релизная ветка удаляется

## Инструменты

Для упрощения работы с Git Flow можно использовать:
- [git flow](https://github.com/nvie/gitflow) (расширение для Git)
- Встроенную поддержку Git Flow в вашей IDE (например, в JetBrains IDE, VS Code с расширениями)
