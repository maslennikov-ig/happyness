## Описание задачи

**Приоритет/Срочность:** Высокий

**Зависимости:** tasks2\task12 (Начало разработки базовой системы аутентификации)

**Контекст и Цель:** Необходимо реализовать механизм безопасной аутентификации пользователей с использованием JWT-токенов. Система должна обеспечивать выдачу access и refresh токенов, их валидацию и механизм обновления. Это позволит обеспечить безопасный доступ к API, управлять сессиями пользователей и поддерживать разные типы клиентов (web, mobile).

## Acceptance Criteria / Подзадачи

1. [ ] Разработать сервис для работы с JWT-токенами

   - [ ] Создать функции для генерации JWT-токенов с разными сроками жизни и payload
   - [ ] Реализовать верификацию токенов с проверкой подписи и срока действия
   - [ ] Разработать структуру payload для access и refresh токенов
   - [ ] Обеспечить безопасное хранение секретных ключей для подписи

2. [ ] Внедрить механизм работы с access токенами

   - [ ] Создать JwtAuthGuard для защиты маршрутов, требующих аутентификации
   - [ ] Реализовать JwtStrategy для Passport.js
   - [ ] Добавить декораторы для получения информации о пользователе из токена
   - [ ] Разработать механизм валидации токенов при каждом запросе

3. [ ] Реализовать систему refresh токенов

   - [ ] Создать механизм выдачи refresh токенов при аутентификации

   - [ ] Добавить хранение и проверку refresh токенов в базе данных/Redis
   - [ ] Разработать механизм инвалидации всех токенов пользователя при выходе из системы

4. [ ] Интегрировать с системой безопасного хранения паролей

   - [ ] Реализовать хеширование паролей с использованием Argon2
   - [ ] Создать сервис для проверки паролей
   - [ ] Разработать механизм миграции с устаревших алгоритмов хеширования
   - [ ] Обеспечить защиту от атак перебора паролей

5. [ ] Разработать API-эндпоинты для аутентификации

   - [ ] Создать контроллер для аутентификации (login, refresh, logout)
   - [ ] Реализовать валидацию входящих данных
   - [ ] Добавить защиту от CSRF-атак
   - [ ] Реализовать механизм блокировки аккаунта после нескольких неудачных попыток входа

6. [ ] Реализовать хранение сессий и cookies
   - [ ] Настроить безопасное хранение refresh токенов в HTTP-only cookies
   - [ ] Реализовать механизм управления сессиями пользователей
   - [ ] Добавить возможность одновременной работы с нескольких устройств

## Тех. Указания

- **Языки и фреймворки:** Node.js 22.x, NestJS 11.x, TypeScript 5.x
- **Библиотеки:**
  - jsonwebtoken для работы с JWT
  - @nestjs/passport и passport-jwt для интеграции с Passport.js
  - argon2 для хеширования паролей
  - cookie-parser для работы с cookies
- **БД и хранение данных:**
  - PostgreSQL (через Prisma) для хранения пользователей
  - Redis для хранения активных refresh токенов и черного списка токенов
- **Архитектурные принципы:**
  - Следовать принципам безопасности OWASP для аутентификации
  - Использовать подход token-based authentication с разделением access и refresh токенов
  - Применять dependency injection для тестируемости компонентов
  - Организовать код в соответствии с [tasks/tasks1/task21_project_structure.md](../../tasks1/task21_project_structure.md)

## Нефункциональные Требования

- **Безопасность:**

  - Соответствие современным стандартам безопасности аутентификации (OWASP)
  - Защита от распространенных атак: brute force, CSRF, XSS, token hijacking
  - Безопасное хранение чувствительных данных (пароли, токены)
  - Применение HTTPS для всех взаимодействий с API

- **Производительность:**

  - Быстрая валидация токенов (<5мс на запрос)
  - Оптимальный размер токенов для минимизации overhead
  - Эффективное использование кэширования для проверки токенов

- **Масштабируемость:**

  - Работа аутентификации в многосерверном окружении (stateless)
  - Распределенное хранение токенов для поддержки горизонтального масштабирования
  - Минимизация блокирующих операций с базой данных

- **Отказоустойчивость:**

  - Корректная обработка сетевых ошибок и сбоев Redis/PostgreSQL
  - Механизм повторных попыток для критических операций
  - Graceful degradation при недоступности компонентов

- **Логирование и мониторинг:**
  - Структурированное логирование операций аутентификации
  - Механизм обнаружения подозрительной активности
  - Сбор метрик для анализа попыток аутентификации

## Потенциальные риски

## Вопросы для Уточнения

1. Какие дополнительные данные следует хранить в payload токенов для работы бизнес-логики?

   - Предварительный ответ: В access токене рекомендуется хранить минимальный набор данных, необходимых для авторизации: ID пользователя, роль, базовые разрешения. Избыточные данные увеличивают размер токена и могут создать проблемы безопасности.

2. Какой срок жизни должен быть у access и refresh токенов?

   - Предварительный ответ: Access токен рекомендуется делать короткоживущим (15-60 минут) для минимизации рисков при компрометации. Refresh токен может иметь срок жизни до 7-30 дней в зависимости от требований безопасности и UX.

3. Требуется ли поддержка нескольких устройств для одного пользователя?
   - Предварительный ответ: Да, система должна поддерживать множественные активные сессии пользователя с разных устройств, с возможностью просмотра и управления ими в профиле пользователя.
