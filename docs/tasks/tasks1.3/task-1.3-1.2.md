# Задача 1.3.2: Разработка компонентов обработки ошибок API

[Правила работы с задачами](../../tasksrules.md)

use context7

## Описание задачи

**ID Задачи/Путь к файлу:** [tasks1.3/task-1.3-1.2.md](../../sprints/sprint1.3.md#задача-12-разработка-компонентов-обработки-ошибок-api)

**Приоритет/Срочность:** Средний

**Зависимости:** task13.1 (Завершение компонентов ядра системы)

**Контекст и Цель:** Разработать централизованную систему обработки ошибок API, которая будет использоваться всеми модулями для предоставления единообразного формата ошибок, логирования и обработки непредвиденных исключений. Это обеспечит консистентный опыт пользователя, упростит клиентскую обработку ошибок и отладку на стороне сервера.

## Acceptance Criteria / Подзадачи

1. [ ] Разработать единую структуру ответов об ошибках

   - [ ] Создать интерфейсы для API-ошибок (ApiError, ErrorResponse)
   - [ ] Реализовать форматирование ошибок по стандартам REST API (RFC 7807)
   - [ ] Добавить метаданные (timestamp, errorId, path) для отладки
   - [ ] Обеспечить локализацию сообщений об ошибках

2. [ ] Создать иерархию классов ошибок для разных типов

   - [ ] Разработать базовый класс ошибки (AppError)
   - [ ] Создать специфические классы для разных категорий ошибок:
     - [ ] ValidationError (ошибки валидации)
     - [ ] AuthenticationError (ошибки аутентификации)
     - [ ] AuthorizationError (ошибки авторизации)
     - [ ] ResourceNotFoundError (ресурс не найден)
     - [ ] ConflictError (конфликты данных)
     - [ ] ExternalServiceError (ошибки внешних сервисов)
     - [ ] UnexpectedError (непредвиденные ошибки)

3. [ ] Реализовать глобальные перехватчики исключений для NestJS

   - [ ] Создать AllExceptionsFilter для обработки всех исключений
   - [ ] Реализовать HttpExceptionsFilter для HTTP-исключений NestJS
   - [ ] Добавить ValidationExceptionsFilter для ошибок валидации
   - [ ] Интегрировать с системой логирования из ядра

4. [ ] Разработать механизм маппинга ошибок

   - [ ] Маппинг исключений ORM в API-ошибки
   - [ ] Маппинг системных ошибок Node.js в API-ошибки
   - [ ] Маппинг ошибок валидации в структурированные ValidationError
   - [ ] Обеспечение сохранения контекста ошибки при маппинге

5. [ ] Внедрить контекстную информацию в обработку ошибок

   - [ ] Разработать механизм добавления контекста к ошибкам
   - [ ] Сохранять информацию о запросе в контексте ошибки (user, request data)
   - [ ] Интегрировать с системой трассировки запросов

6. [ ] Интегрировать систему обработки ошибок с документацией API
   - [ ] Добавить описание возможных ошибок в Swagger/OpenAPI
   - [ ] Создать примеры ответов для разных типов ошибок
   - [ ] Документировать коды ошибок и их значения

## Тех. Указания

- **Языки и фреймворки:** Node.js 22.x, NestJS 11.x, TypeScript 5.x
- **Библиотеки:** class-validator для валидации, class-transformer для трансформации
- **Архитектурные принципы:**
  - Следовать принципам из документа API [tasks/tasks1/task23_api_contracts.md](../../tasks1/task23_api_contracts.md)
  - Обеспечить обратную совместимость в случае изменения формата ошибок
  - Использовать dependency injection для гибкости и тестируемости
  - Организовать код в соответствии с [tasks/tasks1/task21_project_structure.md](../../tasks1/task21_project_structure.md)

## Нефункциональные Требования

- **Безопасность:**

  - Никакой чувствительной информации (пароли, токены, секреты) в сообщениях об ошибках
  - Минимизация деталей реализации в ответах клиентам
  - Защита от различных видов атак, использующих ошибки (error-based attacks)

- **Удобство разработки:**

  - Простой API для создания и обработки пользовательских ошибок
  - Понятная документация и примеры использования
  - Совместимость с инструментами разработки (IDE подсказки, типизация)

- **Логирование:**

  - Детальное логирование ошибок для отладки с контекстом
  - Разные уровни логирования в зависимости от типа ошибки
  - Интеграция с системой мониторинга для критических ошибок

- **Производительность:**

  - Минимальное влияние на время ответа API (<10мс на обработку ошибки)
  - Эффективное использование памяти при обработке ошибок
  - Оптимальная сериализация ответов об ошибках

- **Локализация:**
  - Поддержка локализованных сообщений об ошибках
  - Определение языка по заголовку Accept-Language
  - Стандартный формат для перевода сообщений

## Вопросы для Уточнения

1. Нужна ли поддержка нескольких языков для сообщений об ошибках?

   - Предварительный ответ: Желательно реализовать базовую поддержку локализации сообщений об ошибках с использованием библиотеки i18n. Начать с поддержки русского и английского языков.

2. Как должны обрабатываться ошибки в асинхронных операциях, например, в фоновых задачах?

   - Предварительный ответ: Асинхронные ошибки должны логироваться, но не отправляться клиенту напрямую. Для мониторинга статуса фоновых задач следует реализовать отдельный API-эндпоинт.

3. Какой уровень детализации должны иметь сообщения об ошибках для разных окружений (dev, test, prod)?
   - Предварительный ответ: В dev и test окружениях можно включать более детальную информацию (стек вызовов, подробный контекст), в prod - минимальную необходимую для диагностики, без раскрытия внутренних деталей реализации.
