# Задача 1.4.2.2: Разработка API для управления пользователями и ролями

[Правила работы с задачами](../../tasksrules.md)

## Описание задачи

**ID Задачи/Путь к файлу:** [tasks1.4/task-1.4-2.2.md](../../sprints/sprint1.4.md#task-14-22-разработка-api-для-управления-пользователями-и-ролями)

**Приоритет/Срочность:** Средний

**Зависимости:**

- task-1.4-1.1 (Разработка системы управления ролями и правами доступа)
- task-1.4-1.2 (Реализация хранения ролей и прав в базе данных)
- task-1.4-2.1 (Улучшение системы аутентификации)

**Контекст и Цель:** Необходимо разработать полноценное REST API для управления пользователями, ролями и правами доступа. Это API будет использоваться как административным интерфейсом, так и другими сервисами платформы для создания, обновления и управления учётными записями пользователей и их правами доступа. Реализация должна учитывать новую систему ролей и прав, разработанную в рамках спринта 1.4, а также улучшенную систему аутентификации. Данное API является критически важным компонентом для обеспечения гибкости и безопасности платформы.

## Acceptance Criteria / Подзадачи

1. [ ] Проектирование API для управления пользователями

   - [ ] Определить требуемые эндпоинты для CRUD операций с пользователями
   - [ ] Разработать структуру запросов и ответов для каждого эндпоинта
   - [ ] Определить механизмы валидации входных данных
   - [ ] Создать OpenAPI/Swagger документацию для API пользователей

2. [ ] Проектирование API для управления ролями

   - [ ] Определить эндпоинты для CRUD операций с ролями
   - [ ] Разработать структуру запросов и ответов для ролевых операций
   - [ ] Спроектировать эндпоинты для назначения/отзыва ролей пользователям
   - [ ] Создать OpenAPI/Swagger документацию для API ролей

3. [ ] Проектирование API для управления разрешениями

   - [ ] Определить эндпоинты для просмотра и назначения разрешений ролям
   - [ ] Разработать структуру запросов для управления разрешениями
   - [ ] Спроектировать механизм для проверки текущих разрешений пользователя
   - [ ] Создать OpenAPI/Swagger документацию для API разрешений

4. [ ] Разработка контроллера пользователей (UserController)

   - [ ] Реализовать эндпоинт создания пользователя (POST /api/users)
   - [ ] Реализовать эндпоинт получения списка пользователей с фильтрацией и пагинацией (GET /api/users)
   - [ ] Разработать эндпоинт получения информации о конкретном пользователе (GET /api/users/{id})
   - [ ] Создать эндпоинт обновления пользователя (PUT/PATCH /api/users/{id})
   - [ ] Реализовать эндпоинт удаления пользователя (DELETE /api/users/{id})

5. [ ] Разработка контроллера ролей (RoleController)

   - [ ] Создать эндпоинт для получения списка всех ролей (GET /api/roles)
   - [ ] Реализовать эндпоинт получения информации о конкретной роли (GET /api/roles/{id})
   - [ ] Разработать эндпоинт создания новой роли (POST /api/roles)
   - [ ] Реализовать эндпоинт обновления роли (PUT/PATCH /api/roles/{id})
   - [ ] Создать эндпоинт удаления роли (DELETE /api/roles/{id})

6. [ ] Разработка API для управления связями пользователей и ролей

   - [ ] Реализовать эндпоинт для назначения роли пользователю (POST /api/users/{userId}/roles)
   - [ ] Создать эндпоинт для отзыва роли у пользователя (DELETE /api/users/{userId}/roles/{roleId})
   - [ ] Разработать эндпоинт для получения всех ролей пользователя (GET /api/users/{userId}/roles)
   - [ ] Реализовать эндпоинт для получения списка пользователей с определенной ролью (GET /api/roles/{roleId}/users)

7. [ ] Разработка API для управления разрешениями

   - [ ] Создать эндпоинт для получения всех разрешений (GET /api/permissions)
   - [ ] Реализовать эндпоинт для назначения разрешений роли (POST /api/roles/{roleId}/permissions)
   - [ ] Создать эндпоинт для отзыва разрешений у роли (DELETE /api/roles/{roleId}/permissions/{permissionId})
   - [ ] Разработать эндпоинт для получения всех разрешений роли (GET /api/roles/{roleId}/permissions)
   - [ ] Реализовать эндпоинт для проверки наличия определенного разрешения у пользователя (GET /api/users/{userId}/permissions/check)

8. [ ] Разработка API для самоуправления профилем пользователя

   - [ ] Реализовать эндпоинт для получения информации о текущем пользователе (GET /api/users/me)
   - [ ] Создать эндпоинт для обновления собственного профиля (PATCH /api/users/me)
   - [ ] Разработать эндпоинт для смены пароля (POST /api/users/me/password)
   - [ ] Реализовать эндпоинт для управления настройками безопасности (POST /api/users/me/security)
   - [ ] Создать эндпоинт для управления активными сессиями (GET/DELETE /api/users/me/sessions)

9. [ ] Интеграция API с системой аутентификации

   - [ ] Обеспечить защиту административных эндпоинтов соответствующими правами доступа

   - [ ] Интегрировать обновление JWT-токенов при изменении ролей пользователя
   - [ ] Реализовать корректное логирование операций с учетными записями и ролями

10. [ ] Реализация расширенной фильтрации и поиска

    - [ ] Добавить фильтрацию пользователей по ролям и другим атрибутам
    - [ ] Реализовать полнотекстовый поиск по пользователям
    - [ ] Добавить сортировку и пагинацию для всех списочных эндпоинтов
    - [ ] Создать механизмы для оптимизации запросов при больших объемах данных

11. [ ] Написание тестов для API
    - [ ] Разработать unit-тесты для контроллеров и связанных сервисов
    - [ ] Создать интеграционные тесты для проверки взаимодействия компонентов
    - [ ] Реализовать E2E тесты для основных сценариев использования API
    - [ ] Добавить тесты производительности для критичных эндпоинтов

## Тех. Указания

- **Языки и фреймворки:** TypeScript, NestJS
- **БД и ORM:** PostgreSQL, Prisma ORM
- **Аутентификация и авторизация:** JWT, RBAC (система ролей и прав доступа)
- **Документация API:** OpenAPI/Swagger
- **Архитектурные принципы:**
  - Следовать RESTful принципам проектирования API
  - Использовать паттерны Repository, Service, Controller для разделения ответственности
  - Обеспечить версионирование API для долгосрочной поддержки
  - Применять DTO (Data Transfer Objects) для валидации и преобразования данных

## Нефункциональные Требования

- **Производительность:**

  - Время отклика API не должно превышать 200 мс для основных операций в 95% случаев
  - Эффективная работа со списками пользователей до 10000 записей
  - Оптимизация запросов к БД для минимизации времени отклика

- **Масштабируемость:**

  - API должно корректно работать при горизонтальном масштабировании
  - Возможность обработки не менее 1000 запросов в минуту
  - Учет вероятного роста количества пользователей и ролей в будущем

- **Безопасность:**

  - Полная защита всех эндпоинтов соответствующими проверками прав
  - Предотвращение всех распространенных атак на API (инъекции, CSRF, XSS и т.д.)
  - Детальное логирование операций с чувствительными данными
  - Соответствие стандартам OWASP API Security Top 10

- **Надежность:**

  - Корректная обработка ошибок с информативными сообщениями
  - Транзакционная целостность при операциях, затрагивающих несколько сущностей
  - Отказоустойчивость при сбоях в работе БД или других компонентов

- **Usability:**
  - Консистентные и интуитивно понятные URL и структура ответов
  - Подробная документация API с примерами запросов и ответов
  - Удобные механизмы для отладки и тестирования API

## Итеративность

Разработка API для управления пользователями и ролями должна быть полностью завершена в рамках спринта 1.4. Критически важно реализовать базовый функционал для CRUD-операций с пользователями и ролями. Если возникнут ограничения по времени, можно отложить реализацию расширенной фильтрации и некоторых дополнительных эндпоинтов на следующие спринты, но только при условии, что это не блокирует основную функциональность.

## Вопросы для Уточнения

1. Нужно ли разрабатывать отдельные API-эндпоинты для разных типов пользователей (Предприниматель, Сотрудник компании, Консьерж-менеджер, Администратор)?

   - Предварительный ответ: Базовые операции с пользователями должны быть унифицированы через единый набор эндпоинтов. Специфическая информация и операции для разных типов пользователей могут быть реализованы через дополнительные поля в запросах/ответах или через специализированные эндпоинты.

2. Требуется ли поддержка массовых операций с пользователями (создание/обновление/удаление нескольких записей одним запросом)?

   - Предварительный ответ: Да, для административных целей полезно реализовать поддержку массовых операций. Рекомендуется добавить эндпоинты для массового создания/обновления/удаления пользователей и назначения ролей с учетом необходимых проверок и транзакционной целостности.

3. Как подробно должны быть представлены разрешения в API (предоставлять ли всю информацию о доступах или только идентификаторы)?
   - Предварительный ответ: В API следует предоставлять полную информацию о разрешениях, включая идентификаторы, названия, описания и связанные ресурсы/действия. Это упростит разработку административных интерфейсов и интеграцию с другими системами. При необходимости можно добавить параметр для получения сокращенной информации.

## Безопасность

- Необходимо обеспечить защиту всех административных эндпоинтов соответствующими проверками прав
- API для управления пользователями и ролями должно быть доступно только аутентифицированным пользователям с соответствующими правами
- Все действия с чувствительными данными должны логироваться с указанием пользователя, выполнившего операцию
- Необходимо предотвращать атаки перебора при поиске пользователей или проверке наличия учетных записей
- Обеспечить защиту от инъекций при фильтрации и поиске, особенно при использовании произвольных параметров
- Чувствительные данные (пароли, токены) никогда не должны включаться в ответы API
- При операциях, которые могут нарушить работу системы, требуется дополнительное подтверждение (например, удаление роли)

- Документировать все эндпоинты с помощью декораторов Swagger/OpenAPI

- Документировать возможные коды ошибок и их значение для каждого эндпоинта
