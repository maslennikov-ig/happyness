## Описание задачи

**ID Задачи/Путь к файлу:** [tasks1.4/task-1.4-1.1.md](../../sprints/sprint1.4.md#task-14-11-разработка-системы-управления-ролями-и-правами-доступа)

**Приоритет/Срочность:** Высокий

**Зависимости:** task-1.3-1.1 (Завершение компонентов ядра системы, включая базовую систему аутентификации)

**Контекст и Цель:** На основе реализованной в предыдущем спринте базовой системы аутентификации необходимо разработать полноценную систему управления ролями и правами доступа (RBAC - Role-Based Access Control). Эта система должна обеспечить разграничение функционала платформы между различными типами пользователей (Предприниматель, Сотрудник компании клиента, Консьерж-менеджер, Администратор платформы). Система RBAC является фундаментальной частью безопасности платформы и необходима для контролируемого доступа к ресурсам и функционалу на всех уровнях приложения: API, бизнес-логика и UI.

## Acceptance Criteria / Подзадачи

1. [ ] Спроектировать систему ролей и разрешений

   - [ ] Определить базовые роли системы: Предприниматель, Сотрудник компании клиента, Консьерж-менеджер, Администратор платформы
   - [ ] Определить набор действий/разрешений для каждой роли в соответствии с ТЗ
   - [ ] Создать матрицу прав доступа, показывающую, какие роли имеют доступ к каким ресурсам и действиям
   - [ ] Разработать схему для возможного расширения системы ролей в будущем

2. [ ] Реализовать модель данных для RBAC в Prisma схеме

   - [ ] Создать модели для ролей (Role)
   - [ ] Создать модели для разрешений (Permission)
   - [ ] Реализовать связи между пользователями, ролями и разрешениями
   - [ ] Создать константы для предопределенных ролей и разрешений

3. [ ] Разработать серверные компоненты RBAC

   - [ ] Создать RolesModule и RolesService для управления ролями
   - [ ] Разработать PermissionsService для управления разрешениями
   - [ ] Разработать AuthzService (авторизация) для проверки прав доступа
   - [ ] Реализовать кеширование проверок прав доступа для повышения производительности
   - [ ] Создать NestJS-гварды для защиты маршрутов на основе ролей и разрешений

4. [ ] Реализовать декораторы для удобства использования RBAC

   - [ ] Создать декоратор @Roles для защиты контроллеров/методов по ролям

   - [ ] Создать декоратор @Resource для привязки контроллеров к ресурсам системы
   - [ ] Доработать обработку метаданных в гвардах для использования декораторов

5. [ ] Интеграция RBAC с существующей системой аутентификации

## Тех. Указания

- **Языки и фреймворки:** TypeScript, NestJS (бэкенд), React/NextJS (фронтенд)
- **БД и ORM:** PostgreSQL, Prisma
- **Аутентификация:** JWT, Passport.js (существующая система)
- **Архитектурные принципы:**
  - Следовать принципам RBAC (Role-Based Access Control)
  - Использовать паттерны Guard, Decorator, Interceptor на бэкенде
  - На фронтенде использовать Context API и хуки для управления доступом
  - Обеспечить слабую связанность компонентов и возможность расширения системы

## Нефункциональные Требования

- **Производительность:**

  - Минимизация излишних проверок прав доступа.
  - Кеширование часто запрашиваемых проверок прав для снижения нагрузки на БД.
  - Проверки прав должны выполняться за время не более 50 мс в 95% случаев.

- **Масштабируемость:**

  - Архитектура должна поддерживать расширение системы ролей в будущем.
  - Должна быть предусмотрена возможность добавления новых типов ролей и разрешений без изменения основной кодовой базы.

- **Безопасность:**

  - Строгая проверка прав на всех уровнях (API, бизнес-логика, UI).
  - Защита от несанкционированного повышения привилегий.
  - Логирование всех попыток несанкционированного доступа.
  - Невозможность обхода проверок прав через прямые запросы к API.

- **Логирование:**

  - Детальное логирование операций с ролями и правами в административной панели.
  - Логирование изменений в ролях и разрешениях пользователей.

- **Usability:**
  - Интуитивно понятный интерфейс для управления ролями и правами в административной панели.
  - Четкая обратная связь при отказе в доступе с объяснением причины.
  - Скрытие недоступных элементов UI для улучшения пользовательского опыта.

## Итеративность

Разработка системы управления ролями и правами должна быть завершена в рамках спринта 1.4. Однако, в рамках спринта может быть сделана первая версия системы с основными функциями, а некоторые аспекты (например, расширенный UI для управления ролями в административной панели) могут быть доработаны в последующих спринтах.

## Вопросы для Уточнения

1. Необходимо ли реализовать управление динамическими правами (изменение прав через UI) или достаточно статической системы ролей на первом этапе?

   - Предварительный ответ: На первом этапе достаточно реализовать статическую систему ролей с предопределенными правами для каждой роли, определенной в ТЗ. Это позволит быстрее выпустить систему в продакшн и упростит логику работы. В будущем можно рассмотреть возможность добавления динамических прав через UI.

2. Как должны обрабатываться конфликты прав, если у пользователя несколько ролей с противоречивыми разрешениями?

   - Предварительный ответ: Следуя принципу "принятия наиболее разрешающего права", если у пользователя есть хотя бы одна роль, предоставляющая доступ к ресурсу или действию, доступ должен быть разрешен, несмотря на ограничения в других ролях. Это соответствует наиболее распространенной практике в системах RBAC.

3. Должна ли система поддерживать временные роли или роли с ограниченным сроком действия?
   - Предварительный ответ: В первой версии это не требуется. Достаточно реализовать постоянные роли. Временные роли могут быть добавлены в будущих обновлениях, если в этом возникнет необходимость.

## Безопасность

- Все проверки прав должны выполняться на стороне сервера, даже если есть клиентская валидация.
- Защита от подделки токенов должна быть обеспечена на уровне JWT (подпись, срок действия).
- Необходимо предотвратить возможность повышения привилегий через манипуляции с запросами.
- Кеширование прав не должно создавать уязвимостей при изменении прав пользователя.
- Следует предотвращать утечку информации через ошибки (например, показывать одинаковые сообщения для несуществующих ресурсов и ресурсов, к которым нет доступа).
