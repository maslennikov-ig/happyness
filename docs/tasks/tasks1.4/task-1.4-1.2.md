# Задача 1.4.1.2: Реализация хранения ролей и прав в базе данных

## Описание задачи

**ID Задачи/Путь к файлу:** [tasks1.4/task-1.4-1.2.md](../../sprints/sprint1.4.md#task-14-12-реализация-хранения-ролей-и-прав-в-базе-данных)

**Приоритет/Срочность:** Высокий

**Зависимости:** task-1.3-1.1 (Завершение компонентов ядра системы, включая базовую систему аутентификации)

**Контекст и Цель:** Необходимо создать структуру данных для хранения информации о ролях и правах доступа в базе данных. Это фундаментальная часть системы управления ролями и правами доступа (RBAC), разрабатываемой в рамках спринта 1.4. Структура должна быть гибкой для возможного расширения системы ролей и прав в будущем, а также должна обеспечивать эффективность запросов для проверки прав доступа пользователей. Правильно спроектированная структура данных позволит эффективно реализовать бизнес-логику авторизации и интегрировать её с существующей системой аутентификации.

## Acceptance Criteria / Подзадачи

1. [ ] Анализ требований и проектирование схемы данных

   - [ ] Определить основные сущности: User (существующая), Role, Permission, UserRole (связь)
   - [ ] Определить атрибуты каждой сущности и типы данных
   - [ ] Спроектировать связи между сущностями (one-to-many, many-to-many)
   - [ ] Разработать ER-диаграмму схемы данных для RBAC

2. [ ] Разработка моделей Prisma для ролей

   - [ ] Создать модель Role с полями: id, name, description, createdAt, updatedAt
   - [ ] Добавить предопределённые роли (Предприниматель, Сотрудник, Консьерж-менеджер, Администратор)
   - [ ] Реализовать связь many-to-many между User и Role

3. [ ] Разработка моделей Prisma для разрешений

   - [ ] Создать модель Permission с полями: id, name, description, resource, action, createdAt, updatedAt
   - [ ] Добавить предопределённые разрешения для каждой роли, согласно ТЗ
   - [ ] Реализовать связь many-to-many между Role и Permission

4. [ ] Реализация дополнительных структур (при необходимости)

   - [ ] Создать модель Resource для представления ресурсов системы (если применимо)
   - [ ] Создать модель для группирования разрешений (если применимо)
   - [ ] Создать модели для аудита изменений прав доступа (если требуется)

5. [ ] Создание и применение миграций Prisma

   - [ ] Сгенерировать файлы миграции Prisma для новой схемы
   - [ ] Проверить корректность созданных миграций
   - [ ] Применить миграции к базе данных
   - [ ] Убедиться в отсутствии потери данных при миграции

6. [ ] Реализация базовых CRUD-операций для ролей и прав

   - [ ] Создать сервисы для управления ролями (создание, чтение, обновление, удаление)
   - [ ] Создать сервисы для управления разрешениями (CRUD)
   - [ ] Реализовать методы для назначения ролей пользователям
   - [ ] Реализовать методы для назначения разрешений ролям

7. [ ] Оптимизация производительности запросов

   - [ ] Создать необходимые индексы для полей, используемых при проверке прав
   - [ ] Оптимизировать запросы для получения прав пользователя
   - [ ] Разработать стратегию кеширования ролей и прав для часто используемых запросов

8. [ ] Создать скрипты начального заполнения (сидирование) для базовых ролей и прав

   - [ ] Разработать скрипт для создания предопределенных ролей
   - [ ] Разработать скрипт для создания предопределенных разрешений
   - [ ] Реализовать назначение разрешений предопределенным ролям
   - [ ] Обеспечить идемпотентность скриптов (безопасный повторный запуск)

9. [ ] Написать тесты для хранения и доступа к данным о ролях и правах
   - [ ] Создать unit-тесты для сервисов управления ролями
   - [ ] Создать unit-тесты для сервисов управления разрешениями
   - [ ] Разработать интеграционные тесты для проверки корректности работы с БД
   - [ ] Создать тесты для проверки миграций и сидирования

## Тех. Указания

- **Языки и фреймворки:** TypeScript, NestJS
- **БД и ORM:** PostgreSQL, Prisma ORM
- **Система управления версиями БД:** Prisma Migrate
- **Архитектурные принципы:**
  - Следовать принципам RBAC (Role-Based Access Control)
  - Использовать Prisma для типобезопасной работы с базой данных
  - Обеспечить высокую производительность запросов по ролям и правам
  - Разделять логику доступа к данным и бизнес-логику

## Нефункциональные Требования

- **Производительность:**

  - Оптимизация запросов для проверки прав доступа (не более 50 мс в 95% случаев)
  - Эффективное использование индексов для полей, используемых при проверке прав
  - Минимизация количества запросов к БД при проверке прав

- **Масштабируемость:**

  - Схема данных должна поддерживать возможность добавления новых типов ролей и разрешений в будущем
  - Архитектура должна позволять легко расширять систему без необходимости изменения существующей структуры данных

- **Безопасность:**

  - Защита от SQL-инъекций при работе с данными (обеспечивается Prisma)
  - Контроль доступа к API для управления ролями и правами
  - Аудит изменений в ролях и правах пользователей

- **Надежность:**
  - Транзакционная целостность при обновлении ролей и прав
  - Обеспечение консистентности данных при операциях с ролями и правами
  - Обработка блокировок и конкурентных запросов к данным

## Итеративность

Разработка структуры данных для хранения ролей и прав должна быть завершена полностью в рамках спринта 1.4, так как это фундаментальная часть системы RBAC. После окончания этой задачи должна быть готова полностью работоспособная база данных для хранения и управления ролями и правами, которая будет использоваться в последующих задачах спринта.

## Вопросы для Уточнения

1. Необходимо ли поддерживать иерархию ролей (роли могут наследовать разрешения от других ролей)?

   - Предварительный ответ: На первом этапе разработки достаточно реализовать плоскую структуру ролей без иерархии. Это упростит реализацию и обеспечит базовую функциональность. В будущем, если возникнет необходимость, можно будет расширить систему для поддержки иерархии ролей.

2. Какие дополнительные атрибуты могут потребоваться для ролей и разрешений помимо основных?

   - Предварительный ответ: Для начальной версии достаточно базовых атрибутов (id, name, description) для ролей и (id, name, description, resource, action) для разрешений. В будущем могут потребоваться дополнительные атрибуты: для ролей - scope (область действия), isSystem (системная/пользовательская), priority (приоритет); для разрешений - conditions (условия применения), effect (allow/deny).

3. Требуется ли возможность динамического создания пользовательских ролей и разрешений через интерфейс администратора?
   - Предварительный ответ: В первой версии системы достаточно статических, предопределенных ролей и разрешений. В будущих версиях можно добавить возможность динамического создания и настройки ролей и прав через административный интерфейс.

## Безопасность

- Использовать параметризованные запросы для всех операций с базой данных (обеспечивается Prisma)
- Реализовать валидацию входных данных для всех операций с ролями и правами
- Обеспечить логирование критичных операций с ролями и правами для аудита безопасности
- Контролировать назначение ролей пользователям с учетом принципа минимальных привилегий
