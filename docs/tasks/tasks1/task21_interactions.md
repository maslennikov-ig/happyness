## Описание взаимодействия компонентов

### 1. Взаимодействие между Frontend и Backend

#### 1.1. HTTP API
- **Описание**: Основной способ взаимодействия между клиентским приложением и бэкендом через RESTful API.
- **Технологии**: HTTP/HTTPS, JSON, REST
- **Интерфейсы**:
  - Аутентификация и управление пользователями
  - CRUD-операции для основных сущностей
  - Специфичные API для каждого модуля

#### 1.2. WebSockets
- **Описание**: Для функций, требующих реального времени (чат, уведомления).
- **Технологии**: WebSockets, Socket.io
- **Интерфейсы**:
  - Чат-сообщения
  - Обновление статусов запросов
  - Системные уведомления

### 2. Взаимодействие между модулями Backend

#### 2.1. Прямые вызовы сервисов
- **Описание**: Модули могут напрямую вызывать сервисы других модулей через DI (Dependency Injection) NestJS.
- **Технологии**: TypeScript, NestJS DI
- **Примеры**:
  - Модуль уведомлений вызывает сервисы модуля пользователей для получения информации о получателях
  - Модуль чата использует сервисы модуля запросов для проверки доступа к чату

#### 2.2. События (Event Bus)
- **Описание**: Асинхронное взаимодействие между модулями через систему событий.
- **Технологии**: NestJS EventEmitter, Redis Pub/Sub
- **Примеры событий**:
  - `request.created` - создан новый запрос
  - `message.sent` - отправлено новое сообщение в чате
  - `payment.succeeded` - успешно проведен платеж

#### 2.3. Модульные интерфейсы
- **Описание**: Каждый модуль предоставляет публичный интерфейс для взаимодействия с ним.
- **Технологии**: TypeScript interfaces, Abstract classes
- **Структура интерфейса модуля**:
  ```typescript
  interface IModule {
    name: string;
    version: string;
    initialize(): Promise<void>;
    getPublicServices(): Record<string, any>;
    getEventSubscriptions(): Record<string, Function>;
    shutdown(): Promise<void>;
  }
  ```

### 3. Взаимодействие с базами данных и внешними сервисами

#### 3.1. Доступ к базе данных
- **Описание**: Централизованный доступ к базе данных через Prisma ORM.
- **Технологии**: Prisma, PostgreSQL
- **Паттерны**:
  - Repository Pattern для инкапсуляции логики доступа к данным
  - Unit of Work для управления транзакциями
  - Кеширование часто запрашиваемых данных в Redis

#### 3.2. Кеширование
- **Описание**: Использование Redis для кеширования данных и состояний.
- **Технологии**: Redis, NestJS Cache Manager
- **Стратегии кеширования**:
  - Кеширование результатов запросов к БД
  - Хранение сессий пользователей
  - Временное хранение промежуточных состояний

#### 3.3. Внешние API
- **Описание**: Взаимодействие с внешними сервисами (платежные системы, email).
- **Технологии**: HTTP/HTTPS, REST, SMTP
- **Принципы**:
  - Использование адаптеров для абстрагирования от конкретных реализаций
  - Механизмы повторных попыток и обработки ошибок
  - Мониторинг доступности внешних сервисов

## Схема потока данных для основных сценариев

### Сценарий 1: Создание и обработка запроса консьерж-сервиса

1. Клиент заполняет форму запроса на фронтенде
2. Frontend отправляет данные через API Gateway в Backend
3. Модуль консьерж-сервиса создает запрос в базе данных
4. Модуль консьерж-сервиса генерирует событие `request.created`
5. Модуль уведомлений подписан на это событие и отправляет уведомления:
   - Внутрисистемное уведомление клиенту
   - Email-уведомление клиенту
   - Уведомление консьерж-менеджерам о новом запросе
6. Модуль аналитики также подписан на событие и обновляет статистику
7. Frontend получает обновления через WebSocket и отображает новый статус

### Сценарий 2: Обмен сообщениями в чате по запросу

1. Пользователь отправляет сообщение через интерфейс чата
2. Frontend отправляет сообщение через WebSocket на Backend
3. Модуль коммуникаций проверяет права доступа через модуль авторизации
4. Сообщение сохраняется в базе данных
5. Модуль коммуникаций генерирует событие `message.sent`
6. Сообщение отправляется всем подключенным участникам чата через WebSocket
7. Модуль уведомлений отправляет email-уведомления участникам, не находящимся онлайн

## Принципы проектирования взаимодействий

1. **Слабая связанность (Low Coupling)**: Модули взаимодействуют через четко определенные интерфейсы и события, минимизируя прямые зависимости.

2. **Высокая связность (High Cohesion)**: Каждый модуль объединяет тесно связанные функциональности и данные.

3. **Асинхронность**: Предпочтение асинхронным взаимодействиям для повышения масштабируемости и отказоустойчивости.

4. **Идемпотентность**: API-операции спроектированы так, чтобы повторные вызовы не приводили к нежелательным побочным эффектам.

5. **Версионирование**: Все API-интерфейсы версионируются для обеспечения обратной совместимости.

6. **Централизованная обработка ошибок**: Единый механизм обработки и логирования ошибок во всех взаимодействиях.

7. **Мониторинг и трассировка**: Все взаимодействия логируются и могут быть отслежены для диагностики проблем.
