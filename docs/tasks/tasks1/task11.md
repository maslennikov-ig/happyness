# Задача 1.1: Создание и настройка репозитория проекта

## ## **Часть 1: Общие правила взаимодействия**

1. **Статус задач:**  
   * Выполнено: \[x\]  
   * В процессе: \[.\]  
   * Заблокировано: \[\!\]  
2. **Утверждение фаз/спринтов:**  
   * Запрос одобрения перед новой крупной фазой/модулем или по завершении задач спринта (например, sprint1.md). Утверждение производится **пользователем** после получения отчета от ИИ.  
   * Для одобрения: резюме работ, список измененных/созданных файлов (с указанием полных путей, например, tasks1/task11.md, и сутью изменений/коммитом), подтверждение Acceptance Criteria, описание проблем/рисков.  
3. **Отчет об изменениях, файловая структура и синхронизация с GitHub:**  
   * У выполненных задач/при утверждении фаз: список измененных/созданных файлов с полными путями.  
   * **Файлы спринтов:** sprintN.md (например, sprint1.md).  
   * **Папки задач:** tasks1/ для спринта 1, tasks2/ для спринта 2, и т.д.  
   * **Файлы задач:** task\<раздел\>\<номер\_в\_разделе\>.md в соответствующей папке спринта (например, спринт 1, раздел 1.1 \-\> tasks1/task11.md; спринт 2, раздел 1.1 \-\> tasks2/task11.md).  
   * Для файлов/групп изменений: суть изменений или коммит (Conventional Commits).  
   * **Синхронизация с GitHub:** После завершения всех задач в рамках своего файла (отмеченных как \[x\]):  
     * **Обязательная проверка:** Перед созданием коммита необходимо запустить все настроенные линтеры (для проверки стиля и потенциальных ошибок) и автоматические тесты (unit, integration и т.д.), относящиеся к измененному коду и функциональности файла.  
     * **Коммит и Push:** Коммит создается только после успешного прохождения всех проверок. Затем выполняется отправка (push) этих изменений в основной удаленный репозиторий GitHub.  
4. **Планирование и выполнение:**  
   * Будущие задачи не отмечать выполненными без запроса.  
   * При предложении плана с отложенными задачами – явно указать.  
5. **Структура и детализация задач:**  
   * Следование порядку задач в файлах спринтов (например, sprint1.md).  
   * Новые *крупные* подзадачи/эпики: полный "Формат представления задачи" (Часть 2), ссылаясь на соответствующий файл задачи (например, tasks1/task11.md). *Мелкие*: краткое описание, чек-бокс в файле задачи. ИИ самостоятельно отмечает выполнение мелких подзадач \[x\], если они не являются блокирующими или ключевыми и не требуют отдельного утверждения.  
   * Единообразие именования и структуры подзадач.  
6. **Документация и ресурсы:**  
   * Ссылки на релевантную документацию с указанием версий (если критично).  
7. **Блокировка задач:**  
   * Указание причины, зависимостей и ожидаемого действия от пользователя для разблокировки.  
8. **Проверка полноты фаз/спринтов:**  
   * Перед запросом на переход: проверка выполнения всех задач фазы/спринта, вкл. нефункциональные требования.  
9. **Комментарии и обоснования:**  
   * Комментарии в коде для сложных/неочевидных участков пишутся на **русском языке**, если иное не указано в стилевых гайдах проекта.  
   * Обоснование тех. решений; для ключевых – рассмотренные альтернативы (кратко упомянуть 1-2 ключевые, если выбор не был абсолютно очевидным).  
10. **Обработка ошибок в коде:**  
    * Корректная обработка, осмысленные сообщения, возможные пути решения.  
11. **Управление зависимостями:**  
    * Точные версии (library==1.2.3), причина добавления.  
    * Использование стандартных менеджеров (requirements.txt, package.json, pom.xml).  
12. **Стиль кода:**  
    * use context7  
    * Общепринятые стандарты (PEP 8, Google Style) или по файлу конфигурации. При неясности – запрос или стандарт языка.  
13. **Ограничения и предположения ИИ:**  
    * Явное указание предположений или ограничений знаний/возможностей.  
14. **Запрос на уточнение:**  
    * Не приступать к задаче при неясностях. Формулировка конкретных вопросов пользователю.  
15. **Проактивные предложения:**  
    * Помимо выполнения поставленных задач, ИИ может предлагать улучшения в кодовой базе, архитектуре или рабочем процессе, если видит такую возможность, кратко обосновывая свои предложения.

### **Часть 2: Формат представления задачи для ИИ (сжатый)**

* **Название:** Краткое, ясное (соответствует заголовку в файле задачи).  
* **ID Задачи/Путь к файлу:** Например, tasks1/task11.md (для спринта 1, раздел 1.1).  
* **Приоритет/Срочность:** (Высокий, Средний, Низкий)  
* **Контекст и Цель:** Зачем? Проблема? Бизнес-цель?  
* **Acceptance Criteria / Подзадачи:** Четкие, измеримые критерии (BDD: Given-When-Then). Подзадачи с \[ \] в файле задачи.  
* **Тех. Указания:** Языки, фреймворки, библиотеки (версии); БД; Архитектура. Версии инструментов (если критично) – уточнять или предлагать последние стабильные.  
* **Примеры:** Вход/выход, UI макеты, аналоги.  
* **Нефункциональные Требования:** Производительность, Масштабируемость, Безопасность, Логирование, Usability. При отсутствии метрик – использовать лучшие практики или уточнять.  
* **Итеративность:** Несколько итераций? Промежуточные результаты? Часть спринта?  
* **Формат Вывода:** Код (файлы/структура), ответ в чате, обновление кода (коммит).  
* **Вопросы для Уточнения:** Вопросы для начала работы (от пользователя или ИИ).  
* **Безопасность:** (для релевантных задач) Валидация ввода, OWASP Top 10, шифрование, параметризованные запросы.  
* **Документирование Кода:** API (JSDoc/Sphinx), сложные алгоритмы, README. Формат комментариев – стандартный для языка или по указанию.  
* **Генерация Тестов:** Типы (unit, integration), покрытие (стремиться к разумному, если не указано), фреймворк (PyTest, JUnit, Jest).  
* **Откат/План Б:** (для крит./риск. задач) Действия при сбое, путь отката, альтернативы. Рекомендовать определить, если не указано.  
* **Измененные файлы (ИИ):** Список файлов с полными путями, описание изменений/коммит.

## Содержание задачи
- [ ] Создать Git-репозиторий для проекта

* **Контекст и Цель:** Необходимо создать и настроить Git-репозиторий для централизованного хранения кода проекта и обеспечения совместной работы команды.

* **Ожидаемый Результат / Детализированные подзадачи:**
  - [ ] Создать Git-репозиторий соответствующий стандартам именования проекта
  - [ ] Настроить .gitignore для исключения временных и генерируемых файлов
  - [ ] Сформировать базовую структуру директорий проекта
  - [ ] Создать первоначальный README.md с описанием проекта
  - **Вход:** Требования к проекту, стандарты именования репозиториев
  - **Выход:** Созданный и настроенный Git-репозиторий с базовой структурой

* **Технологические Указания:** 
  - Использовать Git в качестве системы контроля версий
  - Обеспечить поддержку ветвления по модели Git Flow

* **Нефункциональные Требования:**
  - Обеспечить безопасный доступ к репозиторию
  - Настроить правила защиты основных веток от прямых коммитов

* **Итеративность:** При необходимости структура репозитория может быть расширена после согласования с командой.

* **Формат Вывода:** Готовый Git-репозиторий с настроенной структурой директорий проекта, корректным .gitignore, защищенными ветками и информативным README.md файлом. Репозиторий должен обеспечивать возможность добавления новых файлов и директорий в соответствии с модульной архитектурой проекта, описанной в ТЗ.

* **Вопросы для Уточнения:**
  - Требуется ли настройка дополнительных permission для команды?
  - Какая модель ветвления будет использоваться (Git Flow, Feature Branch, и т.д.)?
  - Требуются ли дополнительные инструкции по работе с репозиторием в README.md?


* **Документирование Кода:** Создать подробный README.md с описанием структуры проекта и инструкциями по настройке.
