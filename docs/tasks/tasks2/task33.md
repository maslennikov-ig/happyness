## Правила работы с задачами

1. **Статус задач:**
   - Выполнено: \[x\]
   - В процессе: \[.\]
   - Заблокировано: \[\!\]
2. **Утверждение фаз/спринтов:**
   - Запрос одобрения перед новой крупной фазой/модулем или по завершении задач спринта (например, sprint1.md). Утверждение производится **пользователем** после получения отчета от ИИ.
   - Для одобрения: резюме работ, список измененных/созданных файлов (с указанием полных путей, например, tasks1/task11.md, и сутью изменений/коммитом), подтверждение Acceptance Criteria, описание проблем/рисков.
3. **Отчет об изменениях, файловая структура и синхронизация с GitHub:**
   - У выполненных задач/при утверждении фаз: список измененных/созданных файлов с полными путями.
   - **Файлы спринтов:** sprintN.md (например, sprint1.md).
   - **Папки задач:** tasks1/ для спринта 1, tasks2/ для спринта 2, и т.д.
   - **Файлы задач:** task\<раздел\>\<номер*в*разделе\>.md в соответствующей папке спринта (например, спринт 1, раздел 1.1 \-\> tasks1/task11.md; спринт 2, раздел 1.1 \-\> tasks2/task11.md).
   - Для файлов/групп изменений: суть изменений или коммит (Conventional Commits).
   - **Синхронизация с GitHub:** После завершения всех задач в рамках своего файла (отмеченных как \[x\]):
     - **Обязательная проверка:** Перед созданием коммита необходимо запустить все настроенные линтеры (для проверки стиля и потенциальных ошибок) и автоматические тесты (unit, integration и т.д.), относящиеся к измененному коду и функциональности файла.
     - **Коммит и Push:** Коммит создается только после успешного прохождения всех проверок. Затем выполняется отправка (push) этих изменений в основной удаленный репозиторий GitHub.
4. **Планирование и выполнение:**
   - Будущие задачи не отмечать выполненными без запроса.
   - При предложении плана с отложенными задачами – явно указать.
5. **Структура и детализация задач:**
   - Следование порядку задач в файлах спринтов (например, sprint1.md).
   - Новые _крупные_ подзадачи/эпики: полный "Формат представления задачи" (Часть 2), ссылаясь на соответствующий файл задачи (например, tasks1/task11.md). _Мелкие_: краткое описание, чек-бокс в файле задачи. ИИ самостоятельно отмечает выполнение мелких подзадач \[x\], если они не являются блокирующими или ключевыми и не требуют отдельного утверждения.
   - Единообразие именования и структуры подзадач.
6. **Документация и ресурсы:**
   - Ссылки на релевантную документацию с указанием версий (если критично).
7. **Блокировка задач:**
   - Указание причины, зависимостей и ожидаемого действия от пользователя для разблокировки.
8. **Проверка полноты фаз/спринтов:**
   - Перед запросом на переход: проверка выполнения всех задач фазы/спринта, вкл. нефункциональные требования.
9. **Комментарии и обоснования:**
   - Комментарии в коде для сложных/неочевидных участков пишутся на **русском языке**, если иное не указано в стилевых гайдах проекта.
   - Обоснование тех. решений; для ключевых – рассмотренные альтернативы (кратко упомянуть 1-2 ключевые, если выбор не был абсолютно очевидным).
10. **Обработка ошибок в коде:**
    - Корректная обработка, осмысленные сообщения, возможные пути решения.
11. **Управление зависимостями:**
    - Точные версии (library==1.2.3), причина добавления.
    - Использование стандартных менеджеров (requirements.txt, package.json, pom.xml).
12. **Стиль кода:**
    - use context7
    - Общепринятые стандарты (PEP 8, Google Style) или по файлу конфигурации. При неясности – запрос или стандарт языка.
13. **Ограничения и предположения ИИ:**
    - Явное указание предположений или ограничений знаний/возможностей.
14. **Запрос на уточнение:**
    - Не приступать к задаче при неясностях. Формулировка конкретных вопросов пользователю.
15. **Проактивные предложения:**
    - Помимо выполнения поставленных задач, ИИ может предлагать улучшения в кодовой базе, архитектуре или рабочем процессе, если видит такую возможность, кратко обосновывая свои предложения.

## Содержание задачи

- [ ] Разработать систему профилирования пользователей на основе их действий

* **Контекст и Цель:** Создать систему, которая анализирует активность пользователей в приложении для формирования их профилей предпочтений, интересов и поведенческих паттернов, что позволит персонализировать контент и функциональность системы для каждого пользователя.

* **Ожидаемый Результат / Детализированные подзадачи:**

  - [ ] Спроектировать модель пользовательского профиля (Сложность: Средняя)
    - **Вход:** Требования к персонализации из ТЗ, доступные пользовательские действия
    - **Выход:** Схема данных для профиля пользователя с атрибутами и весами
  - [ ] Реализовать механизм сбора и анализа пользовательских действий (Сложность: Высокая)
    - **Вход:** Модель профиля, точки взаимодействия пользователя с системой
    - **Выход:** Система трекинга и обработки пользовательской активности
  - [ ] Создать алгоритмы для формирования и обновления профилей (Сложность: Высокая)
    - **Вход:** Собранные данные о действиях пользователей, модель профиля
    - **Выход:** Алгоритмы для динамического обновления пользовательских профилей
  - **Вход:** Требования к персонализации из ТЗ (Раздел 9.2)
  - **Выход:** Система профилирования пользователей на основе их активности

* **Технологические Указания:**

  - Использовать событийно-ориентированную архитектуру для отслеживания действий
  - Применить алгоритмы кластеризации для выявления поведенческих паттернов
  - Реализовать механизм весов для различных типов действий
  - Настроить инкрементальное обновление профилей для актуальности данных

* **Нефункциональные Требования:**

  - Минимальное влияние на производительность пользовательского интерфейса
  - Обеспечение приватности данных и соответствие требованиям GDPR
  - Масштабируемость системы для обработки больших объемов данных

* **Итеративность:** Начать с базового профилирования основных действий, постепенно расширяя охват и сложность анализа.

* **Формат Вывода:** Полностью функциональная система профилирования пользователей, включающая модель данных профиля, механизмы сбора и анализа действий, а также алгоритмы формирования и динамического обновления профилей. Система должна предоставлять API для получения профиля пользователя и его атрибутов для использования в других компонентах персонализации. Также должна быть реализована панель администратора для анализа профилей пользователей и настройки параметров профилирования.

* **Вопросы для Уточнения:**

  - Какие конкретные действия пользователя наиболее важны для профилирования?
  - Какая степень детализации профиля требуется для эффективной персонализации?
  - Нужно ли учитывать временные характеристики действий (например, время суток)?
  - Требуется ли забывание устаревших действий в профиле?

* **Фокус на Безопасности:**

  - Обеспечить анонимизацию или псевдонимизацию чувствительных данных
  - Реализовать механизмы для управления пользователем своими данными профиля
  - Настроить аудит доступа к профилям пользователей

* **Документирование Кода:**

  - Подробно документировать модель профиля и её атрибуты
  - Создать руководство по интерпретации данных профиля

* **Генерация Тестов:**

  - Разработать тесты для проверки корректности формирования профилей
  - Создать сценарии симуляции пользовательских действий для тестирования

* **Контекст и Цель:** Создать систему, которая собирает обратную связь о качестве персонализации (явную и неявную) и использует её для постоянного улучшения алгоритмов профилирования и рекомендаций, обеспечивая адаптивность и самообучение системы персонализации.

  - [ ] Создать механизмы корректировки алгоритмов на основе обратной связи (Сложность: Высокая)
    - **Вход:** Данные обратной связи, алгоритмы персонализации
    - **Выход:** Система динамического обновления параметров алгоритмов
  - [ ] Разработать мониторинг качества персонализации (Сложность: Средняя)
    - **Вход:** Метрики эффективности, данные обратной связи
    - **Выход:** Дашборд и алерты для отслеживания качества персонализации
  - **Вход:** Система персонализации из предыдущих задач, требования к адаптивности
