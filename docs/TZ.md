## 1. Введение

### 1.1. Назначение документа

Настоящее Техническое Задание (ТЗ) определяет требования к разработке Платформы для Предпринимателей. Документ предназначен для команды разработки, включая ИИ-ассистентов, и служит основным руководством для проектирования, разработки, тестирования и внедрения платформы.

### 1.2. Миссия и Цели Платформы

- **Миссия Проекта (долгосрочная):** Сделать 1 миллион человек счастливее к 2030 году.
- **Цель Платформы (долгосрочная):** Предоставить предпринимателям комплексный инструмент ("единое окно") для эффективного управления бизнесом, снижения стресса, экономии времени и ресурсов, а также создания условий для личного благополучия и благополучия команды.
- **Бизнес-цель (долгосрочная):** Выйти на чистый доход 10 млн рублей в месяц.
- **Цель Первой Полноценной Версии (ориентировочно 40 недель):** Запустить функционально насыщенную версию платформы, предоставляющую предпринимателям возможность решать широкий спектр операционных задач через консьерж-сервис, с доступом к проверенным подрядчикам, базе знаний, шаблонам и инструментам аналитики. Собрать обратную связь для дальнейшего развития и масштабирования.

### 1.3. Целевая аудитория

- **Предприниматели (владельцы малого и среднего бизнеса) в РФ.**
- **Их команды.**

### 1.4. Определения и Аббревиатуры

- **Платформа:** Разрабатываемый онлайн-сервис.
- **Пользователь:** Любое лицо, взаимодействующее с Платформой.
- **Предприниматель:** Основной клиент Платформы, владелец бизнеса, обладающий соответствующей ролью в системе.
- **Сотрудник Компании Клиента:** Пользователь, приглашенный Предпринимателем, с соответствующей ролью.
- **Консьерж-менеджер:** Сотрудник Платформы, обрабатывающий запросы клиентов, с соответствующей ролью.
- **Администратор Платформы:** Суперпользователь системы с соответствующей ролью.
- **Подрядчик:** Проверенный внешний специалист/компания из базы Платформы.
- **ЛК:** Личный кабинет.
- **API:** Программный интерфейс приложения (Application Programming Interface).
- **UI:** Пользовательский интерфейс (User Interface).
- **UX:** Пользовательский опыт (User Experience).
- **CRUD:** Create, Read, Update, Delete – базовые операции с данными.
- **TZ:** Техническое Задание.
- **ФЗ-152:** Федеральный закон "О персональных данных".
- **WCAG:** Web Content Accessibility Guidelines (Руководство по обеспечению доступности веб-контента).
- **IaC:** Infrastructure as Code (Инфраструктура как код).
- **PWA:** Progressive Web Application (Прогрессивное веб-приложение).

## 2. Общие Требования к Платформе

### 2.1. Обзор Платформы

Платформа представляет собой модульное веб-приложение, доступное через браузер. Система состоит из ядра и набора функциональных модулей, что обеспечивает гибкость, масштабируемость и возможность независимого развития компонентов.

> **Примечание:** Детальная архитектурная документация доступна в [docs/architecture.md](architecture.md).

**Ядро системы** включает в себя:

- Центральную архитектуру и общую инфраструктуру приложения.
- Базовую систему аутентификации и авторизации с управлением ролями.
- Систему управления пользователями и компаниями.
- Модульный фреймворк, обеспечивающий интеграцию и коммуникацию между модулями.
- Общие сервисы (кеширование, логирование, мониторинг, обработка ошибок, уведомления).
- Стандартизированное API для расширения функциональности через модули.

**Функциональные модули** (подключаемые к ядру):

- Модуль консьерж-сервиса (запросы и их отслеживание).
- Модуль коммуникаций (внутренний чат для общения по запросам).
- Модуль тарификации и платежей (подписки и разовые услуги).
- Модуль базы подрядчиков.
- Модуль шаблонов документов и базы знаний.
- Модуль дашбордов и информационных панелей.
- Модуль уведомлений (централизованная система уведомлений).
- Модуль аналитики (базовая для пользователей и расширенная для администраторов).
- Административный модуль для управления системой.

Такая модульная архитектура обеспечивает:

- Возможность независимой разработки и обновления отдельных модулей.
- Более легкое масштабирование системы.
- Высокую отказоустойчивость (проблемы в одном модуле не влияют на работу других).
- Гибкость в настройке функциональности под разные категории пользователей.
- Упрощенное внедрение новых функций в будущем.

### 2.3. Требования к производительности

- Время ответа сервера на типовые запросы API: не более 500 мс (95-й перцентиль).
- Время загрузки основных страниц для пользователей с типичным интернет-соединением (First Contentful Paint - FCP): не более 2 секунд.
- Платформа должна выдерживать нагрузку до 500-1000 одновременно активных пользователей без существенной деградации производительности (целевой показатель для первой полноценной версии, требует уточнения и нагрузочного тестирования).
- **Оптимизация Frontend:**
  - Использование Server Components в Next.js для уменьшения размера бандлов и улучшения TTFB.
  - Стратегии разделения кода (code splitting) для уменьшения размера первоначальной загрузки.
  - Оптимизация изображений через `next/image` и использование современных форматов (WebP, AVIF).
  - Использование `React.memo`, `useMemo`, `useCallback` для предотвращения ненужных ререндеров.
  - Применение стратегии загрузки данных SWR (stale-while-revalidate) или аналогичных через TanStack Query.
  - Skeleton UI и Lazy Loading для улучшения восприятия загрузки.
- **Оптимизация Backend:**
  - Эффективное использование кеширования (Redis, in-memory) согласно стратегии в разделе 2.2.
  - Оптимизация SQL запросов, использование индексов в PostgreSQL.
  - Реализация механизма HTTP-кеширования через использование заголовков ETag и Cache-Control.
  - Применение стратегии DataLoader или аналогичных для решения проблемы N+1 запросов при работе с GraphQL (если будет использоваться) или сложными REST-запросами.
  - Пагинация, ограничение объема данных и ленивая загрузка вложенных объектов.
  - Асинхронная обработка длительных операций (например, генерация отчетов, массовые рассылки) с использованием очередей сообщений (например, RabbitMQ, Kafka - для будущих улучшений, если потребуется).

### 2.4. Требования к безопасности

- **Соблюдение законодательства:**
  - Соблюдение ФЗ-152 в части сбора, хранения и обработки персональных данных пользователей из РФ.
  - Получение явного согласия пользователей на обработку персональных данных при регистрации.
  - Предоставление пользователям возможности запроса на удаление их персональных данных.
- **Защита от веб-уязвимостей (согласно OWASP Top 10 и новее):**
  - Защита от внедрения (инъекций): параметризованные запросы, использование ORM.
  - Защита от XSS (Cross-Site Scripting): экранирование вывода, использование Content Security Policy (CSP).
  - Защита от CSRF (Cross-Site Request Forgery): использование CSRF-токенов (например, double submit cookie или synchronizer token pattern).
  - Защита от Broken Authentication: сложные пароли, многофакторная аутентификация (MFA - рассмотреть для последующих этапов), безопасное управление сессиями и токенами.
  - Защита от Broken Access Controls: строгая проверка прав доступа на каждом уровне (API, сервисы, данные).
  - Security Misconfiguration: регулярный аудит конфигураций.
  - Vulnerable and Outdated Components: своевременное обновление зависимостей.
  - Identification and Authentication Failures.
  - Software and Data Integrity Failures.
  - Server-Side Request Forgery (SSRF) Protection.
- **Передача и хранение данных:**
  - Использование HTTPS (TLS 1.3+) для всего трафика.
  - Хранение паролей в хэшированном виде с использованием современных алгоритмов (Argon2id предпочтительно).
  - Безопасность платежных данных: интеграция с платежным шлюзом должна соответствовать стандартам PCI DSS.
  - Шифрование критически важных данных в базе данных "at rest" и "in transit".
- **Управление доступом:**
  - Разграничение прав доступа на основе ролей (RBAC).
  - Принцип наименьших привилегий.
  - Автоматический выход из системы после периода неактивности.
  - Контроль учетных записей: блокировка после множественных неудачных попыток входа, аудит действий пользователей.
- **Логирование и мониторинг безопасности (см. также раздел 11.4):**
  - Журналирование всех критических действий и событий безопасности.
  - Регулярный анализ журналов безопасности, настройка SIEM (для зрелой системы).
  - Система оповещений о подозрительной активности.
- **Защита данных и файлов:**
  - Регулярное резервное копирование данных (см. Раздел 9.2).
  - Антивирусная проверка загружаемых файлов.
  - Верификация типов файлов.
  - Ограничение размера загружаемых файлов.
- **Безопасность Frontend:**
  - Sanitization пользовательского ввода.
  - Secure Cookie настройки.
- **Безопасность Backend:**
  - Rate limiting и защита от DDoS-атак (на уровне инфраструктуры и приложения).
  - Ротация JWT секретов и других ключей.
  - Использование `helmet` или аналогичных библиотек.
  - Корректная настройка CORS.
  - Регулярное проведение аудитов безопасности и penetration testing.

### 2.5. Требования к масштабируемости

- Архитектура должна быть спроектирована с учетом значительного роста количества пользователей и данных.
- Горизонтальное масштабирование для бэкенд-сервисов (stateless-архитектура, использование контейнеризации и оркестрации, например, Kubernetes - для будущих улучшений).
- Масштабируемые облачные сервисы для хостинга, базы данных, кеша, хранилища файлов.

### 2.6. Требования к надежности и доступности

- Доступность платформы: не менее 99.9% в месяц.
- Обеспечить отказоустойчивость всех ключевых компонентов системы (репликация БД, балансировка нагрузки, резервные инстансы сервисов).

### 2.7. Требования к пользовательскому интерфейсу (UI/UX)

- Интерфейс должен быть интуитивно понятным, современным, стильным и адаптивным. Использование `shadcn/ui` и Tailwind CSS должно способствовать этому.
- Дизайн должен быть чистым, профессиональным и вызывать доверие.
- Обеспечить консистентность элементов управления и навигации по всей платформе.
- **Стратегия для мобильных устройств:**
  - **Основной подход:** Полностью адаптивный веб-дизайн, обеспечивающий комфортную работу на смартфонах и планшетах.
  - **PWA (Progressive Web Application):** Рассмотреть внедрение PWA-технологий для улучшения пользовательского опыта на мобильных устройствах (возможность установки на главный экран, работа оффлайн для некоторого контента, push-уведомления, если применимо).
  - **Нативные мобильные приложения (iOS, Android):** Разработка нативных приложений может быть рассмотрена на более поздних этапах развития платформы, на основе анализа пользовательского спроса, специфических потребностей в мобильных функциях (например, глубокая интеграция с ОС, специфичные API устройств) и бизнес-целесообразности.
- Основные пользовательские сценарии должны выполняться за минимальное количество шагов.
- Предусмотреть четкую обратную связь на действия пользователя.
- **Для ключевых экранов ИИ должен сначала предложить базовую структуру и расположение элементов с использованием компонентов `shadcn/ui`, которые затем могут быть утверждены или скорректированы.**
- **Для Административной Панели ожидается функциональный и удобный UI, позволяющий эффективно управлять всеми аспектами платформы. Может потребоваться более сложный дизайн и расширенная аналитика по сравнению с MVP.**
- Требования к доступности интерфейса описаны в Разделе 10.

### 2.8. Требования к браузерам и устройствам

- Поддержка последних двух версий основных браузеров: Google Chrome, Mozilla Firefox, Safari, Edge, Яндекс.Браузер.
- Корректное отображение на экранах с разрешением от 320px в ширину (мобильные) до Full HD (1920px) и выше (десктоп).

### 2.9. Язык Платформы

- Основной язык интерфейса и всего контента: **Русский**.
- Предусмотреть архитектурную возможность добавления других языков в будущем.

### 2.10. Функционал для последующих этапов разработки

Следующие функции и модули могут быть реализованы на последующих этапах развития платформы, после запуска первой полноценной версии:

- Полноценный Конструктор документов с динамической генерацией.

## 4. Функциональные Требования

### 4.1. Модуль Пользовательского Управления и Доступа

#### 4.1.1. Регистрация Предпринимателя

- **Описание:** Пользователь может зарегистрироваться на платформе как Предприниматель.
- **Поля формы регистрации:** Email (логин), Пароль, Повтор пароля, Имя, Фамилия, Название компании, ИНН компании (опционально, но предусмотреть).
- **Процесс:**
  1.  Пользователь заполняет форму.
  2.  Система проверяет уникальность Email.
  3.  Система проверяет валидность данных (сложность пароля, корректность Email).
  4.  Создается учетная запись Пользователя с ролью "Предприниматель" и связанная с ним Компания.
  5.  (Желательно) Отправляется Email для подтверждения регистрации. Пользователь должен перейти по ссылке в письме для активации аккаунта.
- **UI:** Отдельная страница регистрации.

#### 4.1.2. Аутентификация Пользователей

- **Описание:** Зарегистрированные пользователи (всех ролей) могут войти в систему.
- **Поля формы входа:** Email, Пароль.
- **Процесс:**
  1.  Пользователь вводит Email и Пароль.
  2.  Система проверяет учетные данные.
  3.  При успехе пользователь перенаправляется в соответствующий раздел ЛК (например, Дашборд для Предпринимателя, интерфейс управления запросами для Консьерж-менеджера).
  4.  Реализовать механизм "Запомнить меня" (через refresh token).
  5.  Реализовать функцию "Восстановление пароля" через Email.
- **UI:** Отдельная страница входа.

#### 4.1.3. Управление Профилем Пользователя и Компании

- **Описание:** Аутентифицированный Пользователь может просматривать и редактировать данные своего профиля. Предприниматель дополнительно может редактировать данные своей компании.
- **Редактируемые поля профиля Пользователя (общие):** Имя, Фамилия, Контактный телефон. Возможность смены пароля.
- **Редактируемые поля компании (только для Предпринимателя):** Название компании, ИНН, Описание деятельности (краткое), Адрес (опционально).
- **UI:** Раздел "Профиль" или "Настройки" в ЛК.

#### 4.1.4. Управление Сотрудниками Компании Клиента (Базовое, для Предпринимателя)

- **Описание:** Предприниматель может приглашать сотрудников своей компании на платформу и управлять их доступом.
- **Функционал:**
  1.  Приглашение нового сотрудника по Email. Сотруднику отправляется ссылка для завершения регистрации (установки пароля и подтверждения данных).
  2.  Список сотрудников компании с указанием их Email и статуса (активен/приглашен).
  3.  Возможность деактивировать/удалить сотрудника из компании (сотрудник теряет доступ к данным компании).
  4.  Все приглашенные сотрудники получают единую роль "Сотрудник Компании Клиента" с предопределенными правами (см. Раздел 3).
- **UI:** Раздел "Команда" или "Сотрудники" в ЛК Предпринимателя.

#### 4.1.5. Система Тарифов и Подписок

- **Описание:** Платформа предоставляет несколько тарифных планов (например, 2-3) с разным набором функций и лимитов.
- **Параметры тарифов (управляются Администратором Платформы):** Название, Цена (ежемесячная/годовая), Описание, Набор доступных функций/лимитов (например, количество запросов в месяц, доступ к определенным категориям подрядчиков/шаблонов, количество сотрудников).
- **Функционал для Предпринимателя:**
  1.  Просмотр доступных тарифных планов и их сравнение.
  2.  Выбор и оплата тарифа (оформление подписки).
  3.  Просмотр текущего тарифа и даты следующего списания.
  4.  Возможность сменить тариф (апгрейд/даунгрейд с соответствующим пересчетом и условиями).
- **UI:** Страница "Тарифы", раздел "Управление подпиской" в ЛК Предпринимателя.

### 4.2. Модуль Управления Запросами и Консьерж-Сервис

#### 4.2.1. Создание Запроса Предпринимателем (или Сотрудником Компании Клиента)

- **Описание:** Пользователь (Предприниматель или Сотрудник Компании Клиента) может создать новый запрос на услугу или консультацию.
- **Поля формы создания запроса:**
  - Тема запроса (краткое название).
  - Категория запроса (выбор из списка, например: Юридические, Финансы, Маркетинг, HR, IT, Административные, Прочее. Список категорий управляется Администратором Платформы).
  - Подробное описание задачи/проблемы.
  - Ожидаемый результат.
  - Опционально: Срочность (выбор из: Низкая, Средняя, Высокая).
  - Опционально: Желаемый срок выполнения (дата).
  - Опционально: Бюджет (если применимо, текстовое поле или диапазон).
  - Опционально: Прикрепление файлов (до 5 файлов, общим размером до 50 МБ, типы: PDF, DOCX, XLSX, JPG, PNG. Реализовать антивирусную проверку при загрузке согласно разделу 2.4).
- **Процесс:**
  1.  Пользователь заполняет форму.
  2.  Система сохраняет запрос со статусом "Новый".
  3.  Запрос становится доступен Консьерж-менеджерам.
  4.  Пользователь получает уведомление о создании запроса (см. Раздел 4.4.2).
- **UI:** Отдельная форма/модальное окно для создания запроса.

#### 4.2.2. Личный Кабинет: Список Запросов и Статусы

- **Описание:** Предприниматель и его Сотрудники могут просматривать список запросов своей компании и их текущие статусы.
- **Отображаемая информация по каждому запросу:** ID, Тема, Категория, Дата создания, Статус, Исполнитель (Консьерж-менеджер, если назначен).
- **Статусы запросов (минимальный набор):**
  - Новый
  - В работе (принят Консьерж-менеджером)
  - Требует уточнения (от Консьерж-менеджера клиенту)
  - Ожидает ответа клиента
  - Передан подрядчику (если применимо, информация для клиента может быть обобщенной)
  - Выполнен
  - Отменен
- **Функционал:**
  1.  Фильтрация запросов по статусу, категории.
  2.  Сортировка запросов по дате создания, статусу.
  3.  Переход к детальному просмотру запроса (включая чат по запросу).
- **UI:** Раздел "Мои запросы" / "Запросы компании" в ЛК.

#### 4.2.3. Интерфейс Консьерж-менеджера: Управление Запросами

- **Описание:** Консьерж-менеджер имеет интерфейс для просмотра и обработки запросов клиентов.
- **Функционал:**
  1.  Список всех "Новых" запросов (неразобранных), а также запросов "В работе" у текущего или других менеджеров (в зависимости от настроек доступа).
  2.  Возможность взять запрос в работу (статус меняется на "В работе", назначается текущий Консьерж-менеджер).
  3.  Просмотр деталей запроса (все поля, прикрепленные файлы).
  4.  Изменение статуса запроса.
  5.  Добавление внутренних комментариев к запросу (невидимых клиенту).
  6.  Поиск и фильтрация запросов (по клиенту, статусу, дате, категории).
  7.  Доступ к Базе Проверенных Подрядчиков для подбора исполнителя.
  8.  Возможность зафиксировать информацию о подобранном подрядчике (внутренне, для отчетности и истории).
- **UI:** Отдельный раздел для Консьерж-менеджеров.

#### 4.2.4. Система Общения (Чат Клиент-Консьерж по Запросу)

- **Описание:** Реализовать простой текстовый чат, привязанный к каждому конкретному запросу.
- **Участники чата:** Клиент (Предприниматель/Сотрудник, создавший запрос или имеющий к нему доступ от компании) и Консьерж-менеджер, работающий над запросом.
- **Функционал:**
  1.  Отправка текстовых сообщений.
  2.  Отображение истории сообщений.
  3.  Уведомление о новых сообщениях (см. Раздел 4.4.2).
  4.  (Опционально) Возможность прикрепления файлов в чат (с соблюдением требований безопасности из раздела 2.4).
- **UI:** Интегрирован в страницу детального просмотра запроса.

### 4.3. Модуль Управления Знаниями и Инструментами

#### 4.3.1. База Проверенных Подрядчиков (Просмотр, контакт через Консьерж-менеджера)

- **Описание:** Предоставить Предпринимателям (и их Сотрудникам, в зависимости от тарифа/настроек) доступ к информации о проверенных Подрядчиках.
- **Наполнение:** 15-20 Подрядчиков для начала, данные вносятся Администратором Платформы. База должна быть расширяемой.
- **Отображаемая информация по Подрядчику (для Клиента):** Название/ФИО, Лого/Фото (если есть), Краткое описание, Специализации/Категории услуг, Описание услуг, Кейсы (текстовое описание, возможно с ссылками на внешние ресурсы), Отзывы (текстовые, добавленные Администратором или агрегированные), Рейтинг (если реализуется, то простой, например, средняя оценка от Администратора или на основе отзывов).
- **Функционал для Предпринимателя/Сотрудника:**
  1.  Просмотр списка Подрядчиков.
  2.  Фильтры: по Специализации/Категории, Нише/Отрасли (если применимо), Рейтингу (если есть), Ключевым словам (поиск по описанию).
  3.  Просмотр детального профиля Подрядчика.
  4.  **Контакт с Подрядчиком:** **Только через Консьерж-менеджера**. На странице Подрядчика кнопка "Запросить контакт" или "Обсудить с консьержем", которая инициирует создание нового запроса или уведомляет Консьерж-менеджера о заинтересованности в данном подрядчике для существующего запроса. Прямые контакты Подрядчиков скрыты от Клиентов.
- **Доступ в зависимости от тарифа (можно упростить для начала):**
  - **Уровень 1 (Базовый):** Ограниченный просмотр (например, только список и краткое описание).
  - **Уровень 2 (Средний/Профи):** Полный доступ к профилям.
- **UI:** Раздел "Подрядчики" или "Эксперты" в ЛК.

#### 4.3.2. Библиотека Шаблонов и Подсказок (Статические файлы)

- **Описание:** Предоставить Предпринимателям (и их Сотрудникам) доступ к коллекции полезных шаблонов документов и инструкций.
- **Наполнение:** 5-10 ключевых шаблонов для начала (например, шаблон договора, NDA, должностной инструкции). Файлы в форматах PDF, DOCX. Загружаются Администратором Платформы. База должна быть расширяемой.
- **Функционал для Предпринимателя/Сотрудника:**
  1.  Просмотр списка доступных шаблонов с названием и кратким описанием.
  2.  Категоризация шаблонов (если необходимо, управляется Администратором).
  3.  Поиск шаблонов по названию, ключевым словам.
  4.  Скачивание выбранного шаблона.
- **Версионирование:** Просто указание даты последнего обновления файла Администратором.
- **UI:** Раздел "Шаблоны" или "База знаний" в ЛК.

### 4.4. Общие Системные Функции

#### 4.4.1. Дашборд Предпринимателя

- **Описание:** Сводная информационная панель для Предпринимателя при входе в ЛК.
- **Содержимое (не настраиваемое пользователем на первом этапе):**
  1.  Количество активных запросов (со ссылкой на список).
  2.  Последние 3-5 уведомлений (см. Раздел 4.4.2).
  3.  Быстрый доступ к созданию нового запроса.
  4.  (Если применимо по тарифу) Информация о доступных квартальных консультациях (может быть упрощено до информационного блока).
  5.  Ключевые виджеты аналитики по запросам/компании (см. Раздел 4.4.4).
- **UI:** Главная страница ЛК Предпринимателя.

#### 4.4.2. Система Уведомлений (Внутрисистемные, Email)

- **Описание:** Централизованная система информирования пользователей о важных событиях на платформе.
- **Каналы:**
  1.  **Внутрисистемные уведомления:** Отображаются в специальном разделе/виджете в интерфейсе Платформы (например, иконка "колокольчик" со счетчиком новых). Должны быть доступны всем ролям пользователей в их ЛК.
  2.  **Email-уведомления:** Отправляются на зарегистрированный Email пользователя.
- **Ключевые события для уведомлений:**
  - Успешная регистрация (Email).
  - Создание нового запроса (внутрисистемное для клиента; возможно, email для Консьерж-менеджеров о новом запросе).
  - Новое сообщение в чате по запросу (внутрисистемное, Email для всех участников чата).
  - Изменение статуса запроса (внутрисистемное, Email для клиента и, возможно, Консьерж-менеджера).
  - Назначение Консьерж-менеджера на запрос (внутрисистемное для клиента).
  - Уведомление о предстоящей оплате подписки (Email для Предпринимателя).
  - Успешная/неуспешная оплата (Email для Предпринимателя).
  - Приглашение нового сотрудника (Email для приглашаемого сотрудника).
- **Настройка уведомлений пользователем:** Минимальная (например, включить/выключить Email уведомления по типам). Возможность отписаться от маркетинговых рассылок.

#### 4.4.3. Платежный Модуль (Интеграция, управление подписками, разовые платежи)

- **Описание:** Обеспечение приема платежей за подписки на тарифы и возможные разовые услуги.
- **Платежный шлюз (РФ):** Интеграция с одним из: ЮKassa, Tinkoff Kassa, CloudPayments. Выбор шлюза должен быть сделан до начала разработки этой части. ИИ должен быть проинструктирован о конкретном API.
- **Валюта:** Только российский рубль (RUB).
- **Функционал:**
  1.  **Управление подписками (для Предпринимателя):**
      - Оформление ежемесячной/годовой (если предусмотрено тарифом) подписки на тариф.
      - Автоматические рекуррентные платежи.
      - Уведомления о предстоящем списании.
      - Обработка неуспешных платежей (повторные попытки списания, уведомления клиенту, затем возможная блокировка платных функций или перевод на бесплатный/ограниченный тариф).
      - Возможность отмены подписки (с учетом условий тарифа).
  2.  **Разовые платежи:** Предусмотреть архитектурную возможность оплаты дополнительных услуг, если такие будут определены (например, "дополнительная консультация" сверх лимита тарифа).
  3.  **История платежей:** Предприниматель может видеть историю своих оплат в ЛК.
  4.  **Счета/Акты для юрлиц (РФ):** Если предполагается оплата от юрлиц по счету (может быть ручным процессом с генерацией счета Администратором), то для оплат картой физлиц – автоматическая генерация PDF квитанций/чеков (через функционал платежного шлюза). Акцент на онлайн-оплату картами.
- **Безопасность:** Платформа не должна хранить полные данные банковских карт. Взаимодействие с платежным шлюзом через защищенные протоколы, использование токенизации карт на стороне шлюза. Соответствие PCI DSS (через использование сертифицированного шлюза).
- **UI:** Раздел "Оплата", "Подписка", "История платежей" в ЛК Предпринимателя.

#### 4.4.4. Аналитика и Отчетность

- **Для Предпринимателя:**
  - Дашборд с ключевыми показателями по запросам (количество в разных статусах, среднее время выполнения, распределение по категориям).
  - Анализ использования услуг подрядчиков (если применимо, количество обращений, оценки).
  - Отчеты по затратам на услуги платформы и подписку.
- **Для Администратора Платформы:**
  - Общая статистика использования платформы (количество активных пользователей, компаний, динамика регистраций, количество созданных запросов).
  - Анализ популярности тарифных планов, шаблонов документов, категорий подрядчиков.
  - Мониторинг активности и производительности Консьерж-менеджеров (количество обработанных запросов, среднее время реакции).
  - Отчеты по финансовым показателям (доходы от подписок, разовых услуг).
  - **Детализированная аналитика пользовательского поведения (интеграция с внешними системами аналитики):**
    - Мониторинг времени, затрачиваемого пользователями на выполнение ключевых сценариев (например, онбординг, создание запроса, поиск и выбор подрядчика, процесс оплаты).
    - Отслеживание "воронок" конверсий по основным пользовательским путям и выявление точек выхода пользователей из системы на этих этапах.
    - Анализ частоты использования различных функций и разделов платформы для определения приоритетов дальнейшего развития, выявления малоиспользуемых или проблемных зон.
    - Сегментация пользователей (например, по тарифному плану, размеру компании, активности) и анализ их поведения в разрезе этих сегментов.

## 5. Нефункциональные Требования для ИИ-разработчика

Данный раздел описывает ожидания от ИИ-ассистента при генерации кода и артефактов проекта.

### 5.1. Качество кода

- **Язык:** Весь код должен быть написан на TypeScript (frontend и backend) с использованием строгой типизации (TypeScript strict mode).
- **Чистота и Читаемость:** Код должен быть чистым, хорошо структурированным, следовать принципам SOLID (где применимо) и DRY. Имена переменных, функций, классов должны быть осмысленными (на английском языке).
- **Комментирование:**
  - Комментарии должны объяснять _почему_ что-то сделано определенным образом, а не _что_ делается (это должно быть очевидно из кода).
  - Публичные API (функции, классы, методы) должны иметь JSDoc/TSDoc комментарии, описывающие их назначение, параметры и возвращаемые значения.
  - Сложные или неочевидные участки кода должны быть прокомментированы.
  - README.md файлы для ключевых модулей и директорий с описанием их назначения.
- **Форматирование:** Использовать автоматические форматеры кода (например, Prettier) и линтеры (например, ESLint с расширенной конфигурацией, включая правила безопасности и доступности) с согласованными конфигурациями для всего проекта. Конфигурационные файлы для них должны быть частью репозитория.
- **Обработка ошибок:** Реализовать корректную обработку ошибок и исключений в соответствии с Разделом 11. Не допускать "тихих" ошибок. Использовать try-catch, глобальные обработчики ошибок (exception filters в NestJS).
- **Code Review практики:** Генерируемый код должен быть легко читаем и понятен для проведения code review. При необходимости, ИИ может предлагать структуру для Pull Request и Issue с чек-листами.

### 5.2. Детализированная стратегия тестирования

- **Общие принципы:**
  - Тестирование является неотъемлемой частью процесса разработки и проводится на всех его этапах.
  - Приоритет отдается автоматизации тестирования для обеспечения скорости и надежности регрессионных проверок.
  - Все новые функции и исправления должны сопровождаться соответствующими тестами.
- **Виды тестирования и их применение:**
  - **Unit-тесты (Модульные тесты):**
    - **Цель:** Проверка корректности работы отдельных модулей, функций, классов, компонентов в изоляции.
    - **Ответственность:** Разработчики.
    - **Инструменты:** Vitest (для Frontend и Backend).
    - **Покрытие:** Не менее 80-85% для новой критически важной бизнес-логики.
  - **Интеграционные тесты:**
    - **Цель:** Проверка взаимодействия между несколькими модулями или компонентами системы (например, сервис + база данных, несколько сервисов бэкенда).
    - **Ответственность:** Разработчики, QA-инженеры.
    - **Инструменты:** Supertest (для API), Testing Library (для групп React-компонентов), Vitest с моками для внешних зависимостей.
  - **Компонентные тесты (Frontend):**
    - **Цель:** Тестирование отдельных UI-компонентов React, их отображения и поведения в различных состояниях.
    - **Ответственность:** Frontend-разработчики.
    - **Инструменты:** React Testing Library, Vitest.
  - **API-тесты (End-to-End для Backend):**
    - **Цель:** Проверка полноты и корректности работы API эндпоинтов (контрактное тестирование, проверка бизнес-логики, обработки ошибок, авторизации).
    - **Ответственность:** QA-инженеры, разработчики.
    - **Инструменты:** Postman (для ручного и автоматизированного), Supertest, или аналогичные фреймворки для автоматизации.
  - **End-to-End тесты (UI/сквозные):**
    - **Цель:** Тестирование полных пользовательских сценариев через UI, имитируя действия реального пользователя.
    - **Ответственность:** QA-инженеры.
    - **Инструменты:** Cypress, Playwright. Автоматизировать ключевые сценарии.
  - **Тестирование производительности:**
    - **Цель:** Оценка скорости отклика, стабильности и масштабируемости приложения под нагрузкой.
    - **Виды:** Нагрузочное тестирование, стресс-тестирование, тестирование стабильности.
    - **Ответственность:** QA-инженеры, DevOps-инженеры.
    - **Инструменты:** k6, JMeter, Gatling. Проводить перед крупными релизами и при внесении изменений, влияющих на производительность.
  - **Тестирование безопасности:**
    - **Цель:** Выявление уязвимостей в системе.
    - **Виды:** Сканирование уязвимостей (SAST, DAST), penetration testing (ручное и автоматизированное).
    - **Ответственность:** Специалисты по безопасности, QA-инженеры, разработчики (базовые проверки). Проводить регулярно и перед релизами.
  - **Тестирование юзабилити (Usability Testing):**
    - **Цель:** Оценка удобства и интуитивности интерфейса для конечных пользователей.
    - **Методы:** Привлечение реальных пользователей (или представителей ЦА) для выполнения задач, сбор обратной связи, A/B тестирование интерфейсных решений.
    - **Ответственность:** UX/UI-дизайнеры, продуктовая команда, QA.
  - **Тестирование доступности (Accessibility Testing):**
    - **Цель:** Проверка соответствия стандартам доступности (WCAG).
    - **Методы:** Автоматизированные инструменты (Lighthouse, axe), ручная проверка с использованием клавиатуры и скринридеров.
    - **Ответственность:** Frontend-разработчики, QA-инженеры.
  - **Регрессионное тестирование:**
    - **Цель:** Предотвращение появления старых ошибок после внесения изменений в код.
    - **Методы:** Запуск полного набора автоматизированных тестов (Unit, интеграционные, API, E2E) перед каждым релизом или значительным обновлением.
- **Процесс тестирования:**
  - **Тестирование на этапе разработки:** Разработчики пишут и запускают unit-тесты и базовые интеграционные тесты локально.
  - **Тестирование в CI/CD:** Автоматический запуск тестов при каждом коммите/пулл-реквесте в основные ветки. Сборка не должна проходить, если тесты не пройдены.
  - **Тестирование на Staging-окружении:** QA-команда (или выделенные тестировщики) проводит комплексное тестирование (функциональное, регрессионное, API, E2E) на окружении, максимально приближенном к production.
  - **Альфа/Бета-тестирование (опционально):** Привлечение ограниченного круга реальных пользователей для тестирования новых крупных функций.
  - **Приемочное тестирование (User Acceptance Testing - UAT):** Проводится заказчиком или представителями бизнеса для подтверждения соответствия разработанного функционала требованиям.
- **Отчетность по тестированию:** Регулярное формирование отчетов о покрытии кода тестами, результатах тестовых прогонов, найденных дефектах.

### 5.3. Следование конвенциям стека и модульной архитектуре

- **Next.js:** Использовать принятые практики Next.js (App Router, Server Components, маршрутизация, получение данных, API routes и т.д.).
- **NestJS:** Следовать архитектурным паттернам NestJS (модули, контроллеры, сервисы, DTO, pipes, guards, interceptors).
- **Модульный подход:** Строго следовать модульной архитектуре, разделяя функциональные области на ядро и отдельные модули с четкими API-контрактами между ними.
- **React:** Использовать функциональные компоненты и хуки.
- **Prisma:** Эффективное использование возможностей Prisma ORM.
- **Принципы модульной разработки:**
  - Каждый модуль должен иметь четко определенную зону ответственности и минимально необходимые зависимости от других модулей.
  - Взаимодействие между модулями происходит через стабильные публичные API или события.
  - Модули должны быть слабо связаны между собой (low coupling) и иметь высокую внутреннюю связность (high cohesion).
  - Информация о компонентах модуля должна быть скрыта от других модулей (инкапсуляция), кроме явно экспортируемых интерфейсов.

### 5.4. Логирование

- Реализовать структурированное логирование событий на бэкенде (например, JSON) для упрощения анализа: запросы к API, ошибки, важные системные события. Использовать Winston или Pino.
- Не логировать чувствительную информацию (пароли, полные токены, избыточные персональные данные).
- Подробнее см. Раздел 11.4.

### 5.5. Конфигурация

- Все конфигурационные параметры (строки подключения к БД, ключи API, секреты JWT, настройки портов и т.д.) должны выноситься в переменные окружения (`.env` файлы). Не допускать хардкодинга конфигурации. Предоставить `.env.example` файл.

### 5.6. Первоначальное Наполнение Данными (Сидинг)

- Для первоначального наполнения Базы Подрядчиков (15-20 записей) и Библиотеки Шаблонов (5-10 файлов) ИИ должен предусмотреть возможность запуска seed-скриптов (например, через Prisma Client Extensions или кастомные скрипты), которые будут заполнять базу данных тестовыми/начальными данными при первом запуске или по команде.
- Формат данных для сидинга (например, JSON или CSV-файлы) будет предоставлен отдельно, или ИИ может предложить структуру на основе Модели Данных (Раздел 6).
- Seed-скрипты должны быть идемпотентными (безопасны для повторного запуска).

### 5.7. Дополнительные Принципы Разработки для ИИ

- **Выбор библиотек и версий:**
  - Всегда сначала производить поиск готовой, активно поддерживаемой библиотеки или компонента, а не разрабатывать аналогичный функционал с нуля.
  - Предпочтение отдается использованию самых новых, но стабильных (LTS или рекомендованных для production) версий библиотек, компонентов и модулей, указанных в технологическом стеке (Раздел 2.2).
  - При возникновении проблем с зависимостями, если обновление до последних стабильных версий невозможно или создает неразрешимые конфликты, следует отказаться от проблемного модуля и найти современную, совместимую альтернативу, а не фиксировать старые или уязвимые зависимости.
- **Архитектура и Качество:**
  - Всегда предлагать архитектурные улучшения или альтернативные варианты реализации, если это может повысить модульность, читаемость, тестируемость или масштабируемость системы.
  - Использовать современные лучшие практики (best practices) для выбранных технологий, структурирование кода по функциональным модулям (feature-based/domain-based).
  - При необходимости обращаться к официальной документации используемых технологий и фреймворков для поиска актуальных и рекомендуемых решений. Ссылаться на ключевые источники при предложении сложных или неочевидных решений.
  - Активно использовать инструменты статического анализа кода (ESLint, TypeScript strict mode) и форматирования (Prettier) для поддержания качества кода.
  - Следовать принципам функционального программирования там, где это улучшает читаемость и тестируемость кода.
- **Безопасность (дополнение к Разделу 2.4):**
  - Для задач, связанных с безопасностью (аутентификация, авторизация, обработка пользовательских данных, файловые операции, интеграции со сторонними сервисами), явно указывать потенциальные риски и предлагать конкретные способы их минимизации в соответствии с OWASP Top 10 и другими релевантными стандартами.
  - Использовать современные библиотеки и практики для обеспечения безопасности: Content-Security-Policy, CSRF токены, Rate limiting, инвалидация сессий, безопасные cookies (httpOnly, SameSite=strict/Lax), sanitization пользовательского ввода.
  - Ограничивать доверие к пользовательским данным и всегда проводить валидацию на сервере, несмотря на клиентскую валидацию.

### 5.9. Управление Техническим Долгом

- **Определение и Идентификация:**
  - Технический долг – это компромисс между скоростью разработки и качеством кода/архитектуры, который в будущем может привести к увеличению затрат на поддержку и развитие.
  - Источники: сознательные решения (для ускорения), несовершенство первоначального дизайна, устаревание технологий, недостаточный рефакторинг.
  - Идентификация через code review, статический анализ кода (SonarQube, ESLint), анализ сложности кода, отзывы команды.
- **Отслеживание и Документирование:**
  - Задачи по устранению технического долга должны фиксироваться в бэклоге проекта (например, с тегом "tech-debt").
  - Каждая задача должна содержать описание проблемы, ее влияние на систему и предложение по решению.
- **Приоритизация и Устранение:**
  - Приоритизация задач по техническому долгу на основе их критичности, влияния на разработку новых функций и бизнес-рисков.
  - Регулярное выделение времени в рамках спринтов/итераций (например, 10-20% времени) на рефакторинг и устранение технического долга.
  - Не допускать накопления критического уровня технического долга.
- **Превентивные меры:**
  - Следование лучшим практикам разработки и принципам чистого кода (SOLID, DRY, KISS).
  - Проведение регулярных code review.
  - Инвестиции в обучение команды и использование современных инструментов.
  - Своевременное обновление зависимостей и библиотек.
  - Архитектурный контроль и принятие взвешенных решений при проектировании.

## 7. API Спецификации

### 7.1. Общие принципы

- API должен быть реализован в стиле RESTful.
- Формат обмена данными: JSON.
- Все эндпоинты должны быть защищены и требовать аутентификации (JWT), кроме публичных (например, регистрация, вход, восстановление пароля, получение списка тарифов).
- Использовать стандартные HTTP-методы (GET, POST, PUT, DELETE, PATCH).
- Использовать стандартные HTTP-статус коды для ответов (см. Раздел 11.2).
- **Стандартизация формата ошибок API:**

  - Все ошибки API должны возвращать JSON объект.
  - **Обязательные поля:**
    - `statusCode`: Number (HTTP статус код, дублируется для удобства клиента).
    - `message`: String (общее описание ошибки, понятное человеку; может быть массивом строк для нескольких сообщений).
    - `error`: String (краткий код или тип ошибки, например, "VALIDATION_ERROR", "UNAUTHENTICATED", "INTERNAL_SERVER_ERROR", "RESOURCE_NOT_FOUND").
  - **Опциональные поля:**
    - `details`: Array of objects или Object (дополнительная информация, например, список ошибок валидации по полям: `[{ "field": "email", "message": "Email is invalid", "code": "INVALID_FORMAT" }]`).
    - `timestamp`: String (ISO 8601 формат времени возникновения ошибки на сервере, например, "2025-05-15T10:30:00.123Z").
    - `path`: String (путь запроса, который вызвал ошибку).
    - `correlationId`: String (уникальный идентификатор запроса для отслеживания в логах).
  - **Примеры:**

    ```json
    // Пример: 400 Bad Request - Ошибка валидации
    {
      "statusCode": 400,
      "message": "Ошибка валидации входных данных.",
      "error": "VALIDATION_ERROR",
      "details": [
        { "field": "email", "message": "Поле Email должно быть действительным адресом электронной почты.", "code": "INVALID_EMAIL_FORMAT" },
        { "field": "password", "message": "Пароль должен содержать не менее 8 символов.", "code": "PASSWORD_TOO_SHORT" }
      ],
      "timestamp": "2025-05-15T10:30:00.123Z",
      "path": "/auth/register",
      "correlationId": "abc123xyz789-correlation-id"
    }

    // Пример: 401 Unauthorized - Ошибка аутентификации
    {
      "statusCode": 401,
      "message": "Пользователь не аутентифицирован. Требуется действительный токен доступа.",
      "error": "UNAUTHENTICATED",
      "timestamp": "2025-05-15T10:32:00.456Z",
      "path": "/users/me",
      "correlationId": "fgh456jkl012-correlation-id"
    }

    // Пример: 500 Internal Server Error - Внутренняя ошибка сервера
    {
      "statusCode": 500,
      "message": "Произошла непредвиденная ошибка на сервере. Пожалуйста, попробуйте позже или обратитесь в поддержку.",
      "error": "INTERNAL_SERVER_ERROR",
      "timestamp": "2025-05-15T10:35:10.789Z",
      "path": "/some/critical-resource",
      "correlationId": "pqr789stu345-correlation-id"
    }
    ```

- Предусмотреть пагинацию для списков, используя query-параметры `page` (номер страницы, начиная с 1, по умолчанию 1) и `limit` (количество элементов на странице, по умолчанию 10, максимум 100). Ответ должен включать информацию об общем количестве элементов (`totalItems`, `totalPages`).
- Предусмотреть фильтрацию и сортировку для списков, где это необходимо. Для сортировки использовать `sortBy` (имя поля для сортировки) и `order` (значения 'asc' или 'desc').
- Версионирование API (например, `/api/v1/...`) является обязательным для обеспечения обратной совместимости (см. Раздел 9.1.1).

### 7.2. Аутентификация API

- Использовать JWT (JSON Web Tokens), передаваемые в заголовке `Authorization: Bearer <token>`.
- Access token должен иметь короткое время жизни (например, 15-30 минут).
- Refresh token должен иметь более длительное время жизни (например, 7-30 дней) и использоваться для обновления access token.
- Refresh token должен храниться безопасно (например, в httpOnly cookie с флагами Secure и SameSite).

### 7.3. Ключевые эндпоинты

- **Auth API (`/api/v1/auth`)**
  - `POST /register` (Регистрация Предпринимателя)
  - `POST /login` (Вход для всех ролей)
  - `POST /refresh-token` (Обновление access токена с помощью refresh токена)
  - `POST /logout` (Инвалидация refresh токена на бэкенде)
  - `POST /forgot-password` (Запрос на сброс пароля)
  - `POST /reset-password` (Установка нового пароля по токену)
  - `POST /verify-email` (Подтверждение email по токену)
- **Users API (`/api/v1/users`)**
  - `GET /me` (Получение данных текущего аутентифицированного пользователя)
  - `PUT /me` (Обновление данных текущего пользователя)
  - `PUT /me/password` (Смена пароля текущего пользователя)
- **Companies API (`/api/v1/companies`) (Доступ для Предпринимателя к своей компании)**
  - `GET /my` (Получение данных компании текущего пользователя-Предпринимателя)
  - `PUT /my` (Обновление данных компании)
  - `POST /my/employees` (Приглашение сотрудника в компанию)
  - `GET /my/employees` (Список сотрудников компании)
  - `DELETE /my/employees/{employeeId}` (Удаление/деактивация сотрудника из компании)
- **Requests API (`/api/v1/requests`)**
  - `POST /` (Создание запроса Клиентом)
  - `GET /` (Список запросов для Клиента своей компании / для Консьерж-менеджера с фильтрами и пагинацией)
  - `GET /{id}` (Детали запроса)
  - `PUT /{id}` (Обновление запроса, изменение статуса Консьерж-менеджером или Клиентом (например, отмена))
  - `POST /{id}/messages` (Отправка сообщения в чат по запросу)
  - `GET /{id}/messages` (Получение сообщений чата по запросу с пагинацией)
  - `POST /{id}/files` (Загрузка файлов к запросу)
- **Contractors API (`/api/v1/contractors`)**
  - `GET /` (Список подрядчиков с фильтрами и пагинацией)
  - `GET /{id}` (Детали подрядчика)
- **DocumentTemplates API (`/api/v1/document-templates`)**
  - `GET /` (Список шаблонов с фильтрами и пагинацией)
  - `GET /{id}/download` (Скачивание файла шаблона)
- **Tariffs API (`/api/v1/tariffs`)**
  - `GET /` (Список доступных тарифных планов для всех)
  - `GET /my-subscription` (Текущая подписка Предпринимателя)
  - `POST /subscriptions` (Оформление/изменение подписки Предпринимателем)
  - `DELETE /subscriptions/my` (Отмена подписки Предпринимателем)
- **Payments API (`/api/v1/payments`)**
  - `GET /my` (История платежей Предпринимателя)
  - `POST /webhook/{paymentGatewayName}` (Webhook от платежного шлюза для обработки статусов платежей и подписок)
- **Notifications API (`/api/v1/notifications`)**
  - `GET /` (Список уведомлений для текущего пользователя с пагинацией)
  - `POST /{id}/read` (Пометить уведомление как прочитанное)
  - `POST /read-all` (Пометить все уведомления как прочитанные)
- **Analytics API (`/api/v1/analytics`)**
  - `GET /user-activity` (Сводная аналитика для текущего пользователя/компании)
  - (Эндпоинты для Администратора будут в /admin/analytics)
- **Admin API (`/api/v1/admin`) - Отдельный набор эндпоинтов для Администратора Платформы, защищенный соответствующей ролью**
  - `/users` (CRUD для пользователей, включая Консьержей)
  - `/companies` (Просмотр и управление компаниями клиентов)
  - `/contractors` (CRUD для подрядчиков)
  - `/document-templates` (CRUD для шаблонов документов)
  - `/categories` (CRUD для категорий запросов, шаблонов, подрядчиков)
  - `/tariffs` (CRUD для тарифных планов)
  - `/requests` (Просмотр всех запросов, управление, назначение Консьержей)
  - `/payments` (Просмотр всех платежей, управление статусами)
  - `/analytics/platform-overview` (Общая аналитика по платформе)
  - `/settings` (Управление глобальными настройками платформы)

## 8. Этапы Разработки и Приемка

### 8.1. Ожидаемый результат Первой Полноценной Версии

Первая полноценная версия платформы считается готовой, когда:

1.  Все функции, описанные в Разделе 4 данного ТЗ как основные для первой версии, реализованы и всесторонне протестированы (согласно стратегии тестирования в Разделе 5.2).
2.  Платформа развернута на production окружении и доступна для клиентов.
3.  Проведены тесты безопасности (согласно Разделу 2.4) и производительности (согласно Разделу 2.3), подтверждающие соответствие требованиям.
4.  Подготовлена пользовательская и техническая документация (согласно Разделу 9.3).
5.  Настроены системы мониторинга, логирования и аналитики (согласно Разделам 9.2 и 4.4.4).
6.  Обеспечена возможность сбора обратной связи от пользователей.
7.  Срок разработки первой полноценной версии не превысил 40 недель (целевой ориентир).

### 8.2. Критерии приемки для отдельных функций

Для каждой функции из Раздела 4 должны быть определены конкретные сценарии использования (User Stories) и критерии приемки (Acceptance Criteria). ИИ-разработчик должен стремиться к тому, чтобы генерируемый код удовлетворял этим критериям.

**Пример User Story + Acceptance Criteria:**

- **User Story (Предприниматель):** "Как Предприниматель, я хочу иметь возможность зарегистрироваться на платформе, используя свой email и пароль, чтобы получить доступ к ее функциям."
- **Acceptance Criteria:**
  1.  Форма регистрации содержит поля: Email, Пароль, Повтор пароля, Имя, Фамилия, Название компании. Поле ИНН компании опционально.
  2.  Валидация на стороне клиента и сервера проверяет корректность Email (формат, уникальность) и сложность пароля (например, мин. 8 символов, наличие букв разного регистра и цифр).
  3.  При успешной регистрации создается новая запись пользователя с ролью "Предприниматель" и связанная с ним компания в БД.
  4.  Пользователь автоматически аутентифицируется и перенаправляется на Дашборд (или на страницу подтверждения Email, если реализовано).
  5.  (Желательно) На Email пользователя отправляется письмо со ссылкой для подтверждения регистрации. Аккаунт не полностью активен до подтверждения.
  6.  При попытке регистрации с уже существующим Email выводится соответствующая ошибка согласно стандарту API (Раздел 7.1).

Детальные User Stories и Acceptance Criteria для каждой функции будут предоставляться итерационно. ИИ может запрашивать их по мере продвижения по задачам.

### 8.3. Процесс Управления Задачами и Взаимодействие с ИИ

Для эффективного взаимодействия с ИИ-ассистентом и управления процессом разработки следует придерживаться следующих принципов и форматов постановки задач:

#### 8.3.1. Общие Принципы Взаимодействия

- **Отслеживание выполнения:** Выполненные задачи или подзадачи отмечаются как `[x]`.
- **Утверждение фаз:** Перед началом следующей крупной фазы разработки или модуля ИИ должен запросить одобрение пользователя (руководителя проекта).
- **Задачи для пользователя-разработчика:** Если в ходе работы ИИ возникают задачи, требующие выполнения человеком-разработчиком (например, настройка специфического окружения, получение API-ключей), ИИ должен четко сформулировать задачу в чате и ожидать подтверждения ее выполнения.
- **Отчет об изменениях:** Рядом с выполненной задачей или в комментарии к ней ИИ должен указывать список созданных или измененных файлов.
- **Планирование:** ИИ не должен отмечать будущие задачи как выполненные до получения явного запроса на их реализацию.
- **Структура и порядок:** Задачи будут предоставляться сгруппированными по фазам или модулям. ИИ должен следовать этому порядку, если не указано иное. При генерации новых подзадач ИИ должен использовать единообразное именование и структуру.
- **Документация и ресурсы:** При необходимости ИИ может добавлять ссылки на релевантную документацию или использованные ресурсы.
- **Блокировка задач:** Если задача заблокирована (например, ожиданием информации или выполнения другой задачи), ИИ должен четко указать причину блокировки и зависимости.
- **Проверка фаз:** Перед запросом на переход к следующей фазе ИИ должен убедиться в полноте выполнения всех задач текущей фазы.
- **Временные метки (опционально):** Для отслеживания прогресса ИИ может указывать примерное время начала и завершения работы над крупными задачами.
- **Комментарии и обоснования:** ИИ должен использовать комментарии в коде для сложных участков и может предоставлять краткие обоснования выбранных решений в чате или в описании задачи, если это необходимо.

#### 8.3.2. Формат Постановки Задач для ИИ

Каждая задача, передаваемая ИИ, должна стремиться к следующей структуре:

- **Контекст и Цель:** Краткое описание цели задачи (Что мы хотим достичь?) и ее контекста (Какая часть системы затрагивается? Какие есть зависимости от других модулей или задач?).
- **Ожидаемый Результат (Acceptance Criteria):** Четкое определение того, что считается успешным выполнением задачи (например, "сгенерирован код модуля X с покрытием unit-тестами не менее Y%", "создана и применена миграция схемы БД для сущности Z", "настроен CI/CD пайплайн, который выполняет сборку, линтинг и запуск тестов").
- **Технологические Указания (если необходимо уточнение сверх общего стека):** Указание конкретных технологий, библиотек, версий (если критично), паттернов проектирования, которые ИИ должен использовать для данной задачи.
- **Примеры (если применимо):** Небольшие примеры кода, структуры данных, ожидаемого формата API ответа или UI элемента.
- **Нефункциональные Требования (в контексте задачи):** Упоминание релевантных нефункциональных требований (производительность, безопасность, читаемость кода, логирование) для конкретной задачи.
- **Итеративность:** Для сложных и объемных задач ИИ может быть предложено разбить их на более мелкие подзадачи или генерировать решение по частям, запрашивая обратную связь и утверждение после каждого этапа.
- **Формат Вывода:** Указание желаемого формата вывода от ИИ (например, "предоставить код в виде отдельных файлов .ts с указанием их путей в проекте", "сгенерировать миграционный файл Prisma schema", "предоставить последовательность команд для Docker CLI").
- **Вопросы для Уточнения:** ИИ поощряется задавать уточняющие вопросы, если задача или ее часть недостаточно ясны.
- **Фокус на Безопасности (для релевантных задач):** Для задач, связанных с обработкой пользовательских данных, аутентификацией, авторизацией или внешними интеграциями, явно указывать на необходимость учета аспектов безопасности (например, "реализовать эндпоинт с учетом защиты от CSRF и XSS", "использовать параметризованные запросы к БД", "обеспечить валидацию всех входящих данных").
- **Документирование Кода:** Требование генерации комментариев к коду (TSDoc/JSDoc) для всех публичных функций, классов, методов и сложной или неочевидной логики.
- **Генерация Тестов:** Для большинства задач по генерации кода (особенно для бэкенд-логики) требовать также генерации соответствующих unit-тестов, стремясь к покрытию, указанному в разделе 5.2.
- **Указание на Файлы:** После выполнения задачи ИИ должен предоставить список всех созданных или значительно измененных файлов.

## 9. Развертывание и Эксплуатация

### 9.1. Требования к Развертыванию

- **Окружения:**
  - **Локальное (Development):** Для разработки и отладки.
  - **Тестовое (Staging):** Окружение, максимально приближенное к production, для проверки новых функций и изменений перед их публикацией.
  - **Продакшн (Production):** Основное рабочее окружение платформы, доступное клиентам.
- **Инфраструктура:**
  - **Хостинг:** Рекомендуется использование облачных провайдеров с присутствием в РФ (например, Yandex.Cloud, SberCloud, VK Cloud, или локальные провайдеры, поддерживающие необходимые технологии).
  - **Сервисы:**
    - **Frontend (Next.js):** Статический хостинг (для SSG частей) или Node.js сервер (для SSR/ISR) с CDN для улучшения скорости доставки контента. Vercel или аналоги.
    - **Backend (NestJS):** Серверные инстансы для API-сервисов (виртуальные машины, контейнеры Docker, управляемые PaaS).
    - **База данных (PostgreSQL):** Управляемый PostgreSQL-сервис с настроенным резервным копированием.
    - **Хранилище файлов (Object Storage):** Облачное хранилище (например, Yandex Object Storage, Amazon S3) для шаблонов документов и загружаемых файлов с возможностью доступа через URL.
  - **Инфраструктура как Код (IaC):** Рекомендуется использование IaC (например, Terraform, Pulumi) для управления облачной инфраструктурой. Docker для контейнеризации, Docker Compose для локальной разработки.
- **CI/CD (Непрерывная Интеграция и Доставка):**
  - Настроить CI/CD пайплайн для автоматизации сборки, тестирования и развертывания приложения (например, с использованием GitHub Actions, GitLab CI, Jenkins).
  - **Рекомендуемый Pipeline:**
    1.  **Проверка кода:** Автоматический запуск при коммитах/слиянии в основные ветки.
        - Линтинг (ESLint).
        - Проверка форматирования (Prettier).
        - Проверка типов (TypeScript).
    2.  **Сборка:**
        - Сборка Next.js приложения.
        - Сборка NestJS приложения (создание Docker-образа).
    3.  **Тестирование:**
        - Запуск Unit-тестов.
        - Запуск Integration-тестов.
        - Запуск API-тестов.
        - (Опционально на этом этапе, обязательно перед релизом) Запуск E2E-тестов.
    4.  **Деплой:**
        - Автоматический деплой на тестовое (Staging) окружение при успешных тестах на develop/staging ветке.
        - Ручное или полуавтоматическое (с подтверждением) развертывание в Production окружение из main/master ветки с использованием выбранной стратегии обновления (см. Раздел 9.1.1).
        - Отслеживание статуса деплоя.

#### 9.1.1. Стратегия безопасного обновления системы

- **Автоматизированные миграции схемы БД:**
  - Использование инструментов управления миграциями БД (например, Prisma Migrate).
  - Каждая миграция должна быть атомарной, тестируемой и, по возможности, иметь обратимый характер или четкий план отката.
  - Миграции должны применяться автоматически в процессе CI/CD перед развертыванием новой версии приложения на Staging и Production окружениях. Перед применением на Production – обязательное резервное копирование БД.
- **Стратегии развертывания для минимизации простоев:**
  - **Blue-Green Deployment:** Является предпочтительной стратегией. Подготовка нового ("green") окружения с новой версией приложения параллельно с работающим ("blue") окружением. После полного тестирования "green" окружения, трафик переключается на него. Старое ("blue") окружение сохраняется на короткое время для возможности быстрого отката.
  - **Canary Releases (для будущих улучшений или специфичных выкаток):** Постепенное направление части трафика на новую версию для мониторинга ее работы на реальных пользователях перед полным развертыванием. Может быть рассмотрено для крупных изменений или рискованных обновлений.
- **Версионирование API:**
  - Обязательное использование версионирования API (например, через URL: `/api/v1/...`, `/api/v2/...` или через заголовки `Accept: application/vnd.example.v1+json`).
  - При внесении обратно несовместимых изменений в API, создается новая версия.
  - Старые версии API должны поддерживаться в течение определенного, заранее оговоренного периода (deprecation policy), с уведомлением клиентов (если есть внешние API-пользователи) о необходимости перехода на новую версию.

### 9.2. Мониторинг и Обслуживание

- **Инструменты мониторинга:**
  - **Технический мониторинг:** Настройка системы мониторинга доступности сервисов, использования ресурсов (CPU, память, диск), времени отклика (например, Prometheus + Grafana, или встроенные решения облачного провайдера).
  - **Мониторинг ошибок:** Интеграция инструмента для отслеживания ошибок в реальном времени (например, Sentry), как указано в технологическом стеке.
  - **Логирование:** Централизованный сбор, хранение и анализ логов (например, ELK Stack, Grafana Loki, или сервисы облачного провайдера).
- **Метрики для отслеживания:**
  - Доступность сервисов (uptime).
  - Время отклика API и загрузки ключевых страниц.
  - Частота и типы возникающих ошибок (HTTP 5xx, 4xx), количество необработанных исключений.
  - Использование ресурсов (CPU, память, место на диске для ВМ/контейнеров и БД, сетевой трафик).
  - Производительность базы данных (время выполнения запросов, количество медленных запросов).
  - **Детализированная аналитика пользовательского поведения (интеграция с системами типа PostHog, Mixpanel, GA4):**
    - Время выполнения ключевых пользовательских сценариев.
    - Воронки конверсий по основным сценариям (например, регистрация, создание запроса, оплата).
    - Точки выхода пользователей из системы (страницы/шаги с высоким % ухода).
    - Частота использования различных функций и разделов платформы.
    - Сегментация пользователей и анализ их поведения.
    - A/B тестирование результатов (если проводится).
- **Обслуживание:**
  - **Резервное копирование данных:** Регулярное (ежедневное или чаще, в зависимости от критичности данных) автоматическое резервное копирование базы данных и хранилища файлов. Проверка возможности и регулярное тестирование восстановления из резервных копий.
  - **Плановые технические работы:** Проведение обновлений ПО (ОС, база данных, зависимости), патчей безопасности и других работ по возможности в нерабочие часы с предварительным уведомлением пользователей (если требуется простой).
  - **Процедура отката (Rollback):** Наличие четкой и протестированной процедуры быстрого отката к предыдущей стабильной версии приложения и состояния БД в случае обнаружения критических проблем после деплоя.
  - **Управление зависимостями:** Регулярный аудит и обновление сторонних библиотек и зависимостей.

### 9.3. Требования к Документации

- **Техническая документация (для команды разработки и поддержки):**
  - Актуальная схема базы данных с описанием ключевых сущностей и связей (может генерироваться из Prisma schema).
  - Описание API (Swagger/OpenAPI, генерируемое из кода NestJS и дополненное комментариями).
  - Инструкции по установке, настройке и запуску проекта на локальном окружении для разработки.
  - Описание архитектуры проекта, ключевых модулей, потоков данных и принятых технических решений.
  - Описание процесса CI/CD и развертывания, включая процедуры отката.
  - Политика управления техническим долгом и бэклог технического долга.
- **Пользовательская документация:**
  - Руководство для Предпринимателей и их Сотрудников (основные функции, сценарии использования, ответы на частые вопросы - FAQ, видеоуроки).
  - Инструкции для Консьерж-менеджеров по работе с запросами, Базой Подрядчиков и другими инструментами платформы.
  - Инструкции для Администратора Платформы по управлению системой, пользователями, контентом и настройками.
  - Документация должна быть на русском языке, легко доступна и регулярно обновляться.

## 10. Требования к Доступности и Инклюзивности (Accessibility)

### 10.1. Базовые Требования к Доступности

Платформа должна стремиться к обеспечению высокого уровня доступности для пользователей с ограниченными возможностями.

- **Соответствие стандартам:**
  - Стремление к соответствию требованиям WCAG 2.1/2.2 уровня AA.
- **Ключевые аспекты:**
  - **Контраст и читаемость:** Достаточный контраст между текстом и фоном для обеспечения читаемости (минимальный коэффициент контрастности 4.5:1 для обычного текста и 3:1 для крупного текста).
  - **Навигация с клавиатуры:** Возможность использовать все основные функции и интерактивные элементы (ссылки, кнопки, поля форм) с помощью только клавиатуры в логической последовательности. Видимый фокус для активных элементов.
  - **Альтернативные тексты:** Предоставление осмысленных `alt`-текстов для всех информативных изображений. Декоративные изображения должны иметь пустой `alt=""` или быть реализованы через CSS.
  - **Семантическая разметка:** Использование правильной семантической разметки HTML (заголовки `<h1>`-`<h6>`, списки `<ul>`/`<ol>`, секции `<section>`, `<nav>`, `<main>`, `<article>`, кнопки `<button>`, ссылки `<a>` и т.д.) для лучшей интерпретации контента вспомогательными технологиями (например, экранными читалками). Использование ARIA-атрибутов там, где это необходимо для улучшения доступности сложных виджетов.
  - **Понятные сообщения об ошибках:** Четкие и понятные сообщения об ошибках валидации форм и других системных ошибках, связанные с соответствующими полями или элементами (см. Раздел 11).
  - **Масштабируемость текста:** Возможность увеличения размера текста до 200% без потери контента или функциональности.
  - **Заголовки страниц:** Уникальные и информативные `<title>` для каждой страницы.
  - **Предсказуемость интерфейса:** Элементы интерфейса должны вести себя предсказуемо.
- **Тестирование:**
  - Регулярное тестирование доступности с использованием автоматизированных инструментов (например, Lighthouse, axe DevTools).
  - Ручная проверка навигации с клавиатуры и работы с экранными читалками (например, NVDA, VoiceOver, JAWS) для ключевых пользовательских сценариев.
  - Привлечение пользователей с ограниченными возможностями для тестирования на поздних этапах.

### 10.2. Аспекты для Улучшения после запуска первой версии

- Расширенное соответствие стандартам WCAG до уровня AA по всем компонентам.
- Более глубокое тестирование с привлечением пользователей с различными ограничениями.
- Реализация полной поддержки навигации с клавиатуры, включая "skip links" (ссылки для пропуска блоков навигации) и корректную последовательность фокуса для всех интерактивных элементов.

## 11. Обработка Ошибок и Исключительных Ситуаций

### 11.1. Общие Принципы Обработки Ошибок

- **Прозрачность для пользователя:**
  - Понятные сообщения об ошибках на русском языке, адаптированные под уровень технических знаний целевой аудитории.
  - По возможности, предоставление четких инструкций о возможных действиях пользователя для исправления ошибок.
  - Избегать отображения технических деталей (трассировки стека, SQL-запросов) в сообщениях для конечных пользователей.
- **Безопасность:**
  - Не раскрывать чувствительную информацию в сообщениях об ошибках (пути к файлам на сервере, детали конфигурации и т.д.).
  - Логировать подробную техническую информацию об ошибках только в защищенных системных логах, недоступных пользователям (см. Раздел 11.4).
- **Единообразие:**
  - Использовать единый формат и стиль сообщений об ошибках по всей платформе (UI и API).
  - Обеспечить консистентную визуальную презентацию ошибок в интерфейсе (например, использование компонентов `shadcn/ui` для уведомлений и алертов).

### 11.2. Типы Ошибок и их Обработка

- **Ошибки валидации форм (HTTP 400/422):**
  - Отображать ошибки рядом с соответствующими полями формы при клиентской валидации (мгновенная обратная связь) и после отправки формы при серверной валидации.
  - Указывать конкретные требования к формату или ограничениям для каждого поля (например, "Поле Email обязательно", "Пароль должен содержать не менее 8 символов").
  - API должен возвращать детализированную информацию об ошибках валидации согласно стандарту (Раздел 7.1).
- **Ошибки аутентификации (HTTP 401 Unauthorized):**
  - Сообщение "Неверный email или пароль" без уточнения, какое именно поле неверно (для предотвращения перечисления пользователей).
  - При истечении срока действия токена – перенаправление на страницу входа или запрос на обновление токена.
  - API должен возвращать ошибку согласно стандарту (Раздел 7.1).
- **Ошибки авторизации (HTTP 403 Forbidden):**
  - Сообщение о недостаточности прав для выполнения действия или доступа к ресурсу.
  - API должен возвращать ошибку согласно стандарту (Раздел 7.1).
- **Ресурс не найден (HTTP 404 Not Found):**
  - Кастомная страница 404 с предложением перейти на главную или воспользоваться поиском (если есть).
  - API должен возвращать ошибку согласно стандарту (Раздел 7.1).
- **Ошибки сервера (HTTP 500 Internal Server Error, 502, 503, 504):**
  - Общее сообщение для пользователя "Произошла внутренняя ошибка сервера. Пожалуйста, попробуйте позже или обратитесь в поддержку."
  - Формировать уникальный идентификатор ошибки (correlation ID), который отображается пользователю (опционально) и обязательно логируется для последующего анализа.
  - Кастомная страница 500. Страница обслуживания (503) для информирования о плановых работах.
  - API должен возвращать ошибку согласно стандарту (Раздел 7.1).
- **Сетевые ошибки (на клиенте):**
  - Информировать пользователя об отсутствии или нестабильности интернет-соединения.
  - Предлагать повторить операцию при восстановлении соединения (если это безопасно и уместно).
- **Бизнес-ошибки (могут использовать HTTP 400/409 Conflict или другие подходящие коды):**
  - Четко описывать бизнес-правила, которые были нарушены (например, "Невозможно создать запрос. Достигнут лимит запросов по текущему тарифному плану", "Данный email уже зарегистрирован").
  - По возможности, предлагать конструктивные пути решения проблемы (например, "Рассмотрите возможность перехода на более высокий тарифный план").
  - API должен возвращать ошибку с соответствующим кодом и деталями согласно стандарту (Раздел 7.1).

### 11.3. Пользовательский Интерфейс для Ошибок

- **Общие требования к UI:**
  - Четкое визуальное выделение сообщений об ошибках (например, цвет, иконки). Компоненты `shadcn/ui` (Alert, Toast) должны использоваться для этого.
  - Использование toast-уведомлений (Sonner, React Hot Toast) для некритичных ошибок или временных сообщений о результатах операций.
  - Для критических ошибок, блокирующих дальнейшую работу, могут использоваться модальные окна или полноэкранные сообщения.
- **Восстановление после ошибки:**
  - Предоставлять возможность отмены или повтора операции, когда это возможно.
  - Сохранять введенные пользователем данные в формах для восстановления при перезагрузке страницы или после ошибки валидации на сервере (если это не противоречит безопасности).

### 11.4. Логирование Ошибок (дополнение к Разделу 5.4)

- **Уровни важности логов (например, стандартные syslog levels или аналоги):**
  - `DEBUG`: Детальная информация для отладки (не для production по умолчанию).
  - `INFO`: Обычные операции, важные события (успешная аутентификация, создание ключевых сущностей).
  - `WARN`: Потенциально проблемные ситуации, некритичные ошибки, подозрительные действия (например, множественные неудачные попытки входа, ожидаемые бизнес-исключения).
  - `ERROR`: Ошибки в работе системы, требующие внимания (большинство необработанных исключений, ошибки API, ошибки взаимодействия с внешними системами).
  - `FATAL` (или `CRITICAL`): Критические ошибки, делающие часть системы или всю систему нефункциональной, требующие немедленного вмешательства.
- **Данные для логирования (структурированный формат, например, JSON):**
  - Временная метка (точная дата и время с миллисекундами и часовым поясом, предпочтительно UTC).
  - Уровень важности (DEBUG, INFO, WARN, ERROR, FATAL).
  - Источник ошибки (модуль, файл, функция, строка кода).
  - Сообщение об ошибке.
  - Трассировка стека (для ERROR и FATAL).
  - Correlation ID (для связи логов одного запроса/операции).
  - Идентификатор пользователя (если аутентифицирован и это не нарушает приватность).
  - IP-адрес и user-agent клиента (с учетом требований приватности и GDPR).
  - Контекст (входные параметры запроса (без чувствительных данных), URL, метод HTTP, заголовки (без чувствительных данных)).
- **Хранение логов:**
  - Обеспечить защиту логов от несанкционированного доступа и модификации.
  - Настроить ротацию и архивацию логов для предотвращения перерасхода дискового пространства и обеспечения возможности анализа за определенный период.
  - Рассмотреть использование централизованной системы управления логами (ELK, Loki, Splunk).
